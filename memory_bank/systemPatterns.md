# NoDrive system patterns (architecture reference)

Status: baseline written 2026-11-13 from the approved plan and the research pass. Anything marked
"to verify in spike" is settled in P0 and this file is updated afterwards. Sources are listed at
the end and cited as `[sN]`; statements that come only from Microsoft Q&A moderators or user
reports are marked **community-reported**.

Scope reminder (v1): browse (lazy placeholders), download (progressive hydration), upload new
files, propagate local delete/rename with guards. In-place editing of existing files is P2, but the
state machine and index already reserve the states it needs.

---

## 1. Overview

```
 +-------------------------------------------------------------------------------------------+
 |  Windows 11 user session (per user, unelevated, unpackaged)                                |
 |                                                                                           |
 |  explorer.exe / any app            NoDrive.Settings.exe (on demand, exits when closed)    |
 |   open / copy / move / delete  ---> sign-in (PKCE), folder choice, pause, conflict list    |
 |          |  (normal file I/O)              |  IPC: named pipe + JSON config file            |
 |          v                                  v                                              |
 |  ===== NTFS volume: %USERPROFILE%\NoDrive (sync root) =====                               |
 |          |  reparse points (placeholders)                                                 |
 |          v                                                                                |
 |  cldflt.sys (kernel minifilter) ---- callbacks ----> CldApi.dll (in-proc, own threadpool) |
 |          ^                                                      |                         |
 |          | CfExecute / CfCreatePlaceholders / CfSetInSyncState  v                         |
 |  +-------+--------------------------------------------------------------------------+    |
 |  |  NoDrive.Engine.exe  (always on, Native AOT, WinExe, no UI framework)             |    |
 |  |                                                                                  |    |
 |  |  [Tray + message-only HWND]   [Supervisor thread]                                |    |
 |  |  [CfApi provider]  --enqueue-->  bounded channels  -->  [Workers]                |    |
 |  |      (callbacks return in us)       |                   hydration x3-4           |    |
 |  |                                     |                   enumeration x1-2         |    |
 |  |  [Local watcher]                    |                   upload x2-3              |    |
 |  |   ReadDirectoryChangesW + USN       v                   delta ingest x1          |    |
 |  |                             [Reconciler: per-item state machine]                 |    |
 |  |                                     |                                            |    |
 |  |            [SQLite index + journal: %LOCALAPPDATA%\NoDrive\index.db]            |    |
 |  |                                     |                                            |    |
 |  |                             [Graph client: HttpClient + STJ source-gen]          |    |
 |  +-------------------------------------+--------------------------------------------+    |
 +----------------------------------------|--------------------------------------------------+
                                          v  HTTPS
                 Microsoft Graph v1.0: /me/drive/root/delta, /items/{id}, downloadUrl (Range),
                 PUT .../content, createUploadSession + uploadUrl, PATCH/DELETE items,
                 login.microsoftonline.com/consumers (auth code + PKCE)
```

Why this shape:

- explorer.exe renders everything (Status column, nav-pane node, progress, "Always keep on this
  device / Free up space"); the engine only answers callbacks, so idle cost is the engine alone
  `[s1]`.
- The provider must be an ordinary per-user desktop process that stays running: hydration from
  session 0 is blocked and an absent provider makes every online-only file fail with
  0x8007016A `[s2] [s3]`. Hence a single always-on engine and no Windows service.
- The UI lives in a second process so no UI framework is ever resident; it is launched with the
  .NET 11 `ProcessStartInfo.StartDetached` / `Process.StartAndForget` APIs `[s4]`.

## 2. Components of the engine

All components live in `src/NoDrive.Engine` except the platform-independent reconciler, index
and abstractions (`src/NoDrive.Core`) and the Graph client (`src/NoDrive.Graph`).

### 2.1 Tray and message loop (`Engine/Shell`)

- Message-only window (`HWND_MESSAGE` parent) + `Shell_NotifyIconW`, generated by CsWin32; a
  classic `GetMessageW` loop on the main thread. Handles `WM_CONTEXTMENU` and `WM_RBUTTONUP`,
  re-adds the icon on the `TaskbarCreated` broadcast after an Explorer restart `[s5]`.
- Owns lifecycle: single-instance mutex, HKCU `Run` autostart, `WM_QUERYENDSESSION` ->
  graceful `CfDisconnectSyncRoot`, never `CfUnregisterSyncRoot` on normal exit `[s6]`.
- Tray menu: pause/resume, open folder, sign in/out, "Free up space in folder..." / "Keep folder
  offline" fallback actions (Insider builds moved the built-in verbs into a per-provider flyout
  `[s7]`), open Settings, exit.

### 2.2 CfApi provider (`Engine/CloudFiles`)

- One `CfConnectSyncRoot` connection per sync root (the platform allows exactly one) `[s3]`,
  flags `CF_CONNECT_FLAG_REQUIRE_PROCESS_INFO | CF_CONNECT_FLAG_BLOCK_SELF_IMPLICIT_HYDRATION`.
- Registered callbacks: `FETCH_DATA`, `CANCEL_FETCH_DATA`, `FETCH_PLACEHOLDERS`,
  `CANCEL_FETCH_PLACEHOLDERS`, `NOTIFY_DELETE`, `NOTIFY_DELETE_COMPLETION`, `NOTIFY_RENAME`,
  `NOTIFY_RENAME_COMPLETION`. Only FETCH_DATA and FETCH_PLACEHOLDERS are mandatory for our
  policies; delete/rename are optional but block the user operation until acked `[s8]`.
- Callbacks are `[UnmanagedCallersOnly]` static methods. They validate arguments, copy the few
  fields they need (`ConnectionKey`, `TransferKey`, `RequestKey`, `FileId`, `FileIdentity`,
  `NormalizedPath`, offsets/lengths, `PriorityHint`, `ProcessInfo`) into a small struct, enqueue
  it to the right bounded channel and return. No I/O, no locks that can wait, no allocation on
  the hot path beyond the struct.
- Completion of a request always happens on a worker via `CfExecute`
  (`TRANSFER_DATA`, `TRANSFER_PLACEHOLDERS`, `ACK_DELETE`, `ACK_RENAME`, `RESTART_HYDRATION`) with
  an explicit `CompletionStatus`. A failing status is the only way to abort a request;
  `CF_OPERATION_ACK_DATA_FLAG_CANCELED` does not exist `[s9]`.
- Implements `IPlaceholderStore` for the Core layer: create placeholders in batches, convert a
  plain file to a placeholder, set in-sync and pin state, dehydrate, read placeholder info, open
  with oplock. Placeholder updates go through `CfOpenFileWithOplock` so the engine never fights
  a user's open handle (plan rule 7).
- Minimises `CfUpdatePlaceholder` (heap corruption on 24H2/25H2, **community-reported**, open
  since Nov 2024 `[s10]`): prefers `CfSetInSyncState` / `CfSetPinState`; the spike decides whether
  `CfUpdatePlaceholder` is used at all (P0 step 4).

### 2.3 Local watcher (`Engine/Watcher`)

- Live: `ReadDirectoryChangesW` on the sync root with a large buffer, including attribute
  changes so that `FILE_ATTRIBUTE_UNPINNED` is observed (Explorer "Free up space" does not raise
  `NOTIFY_DEHYDRATE`, **community-reported**, Microsoft External Staff reproduced with CloudMirror
  `[s11]`); the engine then dehydrates itself with `CfDehydratePlaceholder` (documented only on an
  archived page but exported and present in Win32Metadata `[s12]`).
- Startup and gap recovery: NTFS USN journal replay from the persisted USN cursor to find
  creates, deletes, renames and writes that happened while the engine was not running; falls back
  to a full tree scan when the journal wrapped `[s13]`. cfapi itself never reports local creates or
  content edits, only delete/rename of placeholders (**community-reported** FAQ `[s13]`).
- Debounces storms (Office save sequences, mass renames) 2-5 s per path, off the callback path,
  and compares size + quickXorHash / eTag before scheduling any upload (plan rule 8).
- Emits `LocalChange` records into a bounded channel consumed by the reconciler.

### 2.4 Graph client (`src/NoDrive.Graph`)

- Implements `IRemoteDrive` over a single static `HttpClient` / `SocketsHttpHandler`; DTOs are
  hand-written with one `JsonSerializerContext` (metadata mode so delta pages can be deserialized
  as a stream) `[s14]`. No Microsoft.Graph SDK (ADR-0004).
- Auth: authorization-code + PKCE against `login.microsoftonline.com/consumers`, system browser,
  loopback listener on `http://localhost:{port}`, refresh token stored with DPAPI; scopes
  `Files.ReadWrite offline_access` `[s15]` (ADR-0003).
- Endpoints (about ten): `GET /me/drive`, `GET /me/drive/root/delta` (+token, `$select`),
  `GET /me/drive/items/{id}` with `$select=id,@microsoft.graph.downloadUrl`, downloadUrl GET with
  `Range`, `PUT .../items/{parent}:/{name}:/content`, `POST .../createUploadSession` + `PUT`/`GET`/
  `DELETE uploadUrl`, `PATCH /items/{id}` (rename/move), `DELETE /items/{id}`,
  `POST /items/{id}/children`, later `GET /me/drive/root/subscriptions/socketIo` `[s16]`.
- One global `ThrottleGate`: any 429/503 with `Retry-After` pauses every worker until the
  deadline; SharePoint/OneDrive do not return IETF RateLimit headers `[s17]`.
- `User-Agent: ISV|<owner>|NoDrive/<version>` on every request `[s17]`.
- The transfer layer (`IContentTransfer`) is isolated so the tempauth-URL retirement on
  2027-04-01 (consumer scope unclear) can be absorbed by switching to bearer `GET /content` `[s18]`.

### 2.5 Reconciler (`src/NoDrive.Core/Reconcile`)

- Owns the per-item state machine (section 4) and is the only writer of item state.
- Inputs: delta pages (remote truth), `LocalChange` records (watcher), cfapi requests (provider),
  journal replays (crash recovery). Output: index mutations and journaled remote mutations.
- Pure, platform-independent code: it talks to `IRemoteDrive`, `IPlaceholderStore`, `IItemIndex`,
  `IJournal`, `IClock`; Windows specifics stay in the Engine project so the reconciler is unit
  tested on macOS/Linux against the fake Graph server.

### 2.6 SQLite index (`src/NoDrive.Core/Index`)

- `winsqlite3.dll` from System32 (zero native payload) via `SQLitePCLRaw.provider.winsqlite3` +
  `Microsoft.Data.Sqlite.Core`, or raw `LibraryImport` of ~15 functions if AOT friction appears
  `[s19]` (ADR-0005, verified in P0 step 5).
- `items(graphId PK, parentId, name, kind, size, eTag, cTag, quickXorHash, remoteLastWrite,
  fileId (NTFS), usn, localState, flags, updatedAt)` with indexes on `parentId`, `fileId` and
  `(parentId, name COLLATE NOCASE)`; `sync_state(deltaLink, nextLink, usnCursor, schema)`;
  `journal` (section 2.7); `conflicts`.
- Implements `IItemIndex`: `GetChildrenPage(parentId, afterName, limit)` for
  FETCH_PLACEHOLDERS, `UpsertBatch`, `MarkDeleted`, lookups by graphId / fileId / path.
- WAL mode, `synchronous=NORMAL`, bounded page cache; the engine never materialises the tree in
  RAM (ADR-0007).

### 2.7 Journal (`src/NoDrive.Core/Journal`)

- Append-only table of intended remote mutations: `(seq, kind, graphId, parentId, name,
  newParentId, newName, localPath, eTag, status, attempts, lastError, createdAt)`.
- Every remote mutation is written here in the same transaction as the local state change that
  motivates it, before anything is sent to Graph (plan rule 6); handlers are idempotent so replay
  after a crash is safe.
- Also records in-flight uploads (uploadUrl, bytes committed) so sessions resume after restart
  `[s20]`.

### 2.8 Supervisor (`Engine/Supervisor`)

- A dedicated low-priority thread with a coarse (>= 1 min when idle, 1 s while requests are
  pending) tick. Watches: callback-to-return latency histogram, per-channel depth, oldest pending
  cfapi request age, `GC.GetGCMemoryInfo().TotalCommittedBytes`, `Process.PrivateMemorySize64`,
  thread count.
- Actions by threshold: fail the oldest pending request with a status (never let it reach the
  platform's 60 s), log stack of the worker holding it, drop caches and run the post-burst GC,
  disconnect/reconnect the sync root, and as a last resort restart the process (Task Scheduler
  "restart on failure" covers hard crashes) (plan rule 9).

## 3. Critical paths

### 3a. Lazy enumeration: FETCH_PLACEHOLDERS from the index

Policy: `PopulationPolicy = PARTIAL`, so Explorer asks for a folder's children the first time it
is opened and only that folder is materialised (ADR-0007).

1. `cldflt.sys` raises `FETCH_PLACEHOLDERS` for `NormalizedPath`, with the search pattern. The
   callback copies `ConnectionKey`, `TransferKey`, `RequestKey`, path, pattern into an
   `EnumerationRequest` and writes it to the enumeration channel (bounded; full channel => fail the
   request immediately with `STATUS_CLOUD_FILE_REQUEST_ABORTED`-class status, to verify exact
   status in spike). Returns.
2. Enumeration worker (1-2 concurrent) resolves the folder's `graphId` from the index by path
   (root path -> root id, then parent chain cached per request), never from Graph.
3. Worker reads children in pages of 500-1000 rows ordered by name from `IItemIndex`, builds
   `CF_PLACEHOLDER_CREATE_INFO[]` (name, size, timestamps, attributes, `FileIdentity` = graphId
   bytes, `IN_SYNC` flag) into pooled buffers and calls
   `CfExecute(TRANSFER_PLACEHOLDERS)` per page with `CF_OPERATION_TRANSFER_PLACEHOLDERS_FLAG_DISABLE_ON_DEMAND_POPULATION`
   only on the final page (so the folder is marked fully populated). Each `CfExecute` resets the 60 s
   timer of all pending requests `[s8]`.
4. Items whose kind is unsupported (OneNote `package` facet, Personal Vault) are skipped and
   recorded as unsupported rather than created as placeholders (ux research gap).
5. A `CANCEL_FETCH_PLACEHOLDERS` sets the request's `CancellationToken`; the worker stops after the
   current page and completes with the cancelled status.
6. Watchdog: deadline 30 s per request (half the platform limit). If exceeded (index locked,
   disk slow) the supervisor completes the request with a failure status. A folder whose
   FETCH_PLACEHOLDERS timed out with 0x800701AA may stop receiving callbacks until Explorer
   restarts (**community-reported** `[s9]`), so timing out is treated as a bug, never a strategy.
7. Acceptance: 30k-child folder answered well inside the deadline from the index alone (P0 step 6).

### 3b. Progressive hydration: FETCH_DATA streamed into TRANSFER_DATA

Policy: `HydrationPolicy = PROGRESSIVE` + `AUTO_DEHYDRATION_ALLOWED`. Progressive providers must
serve random offsets, not just sequential from zero `[s1]`.

1. `FETCH_DATA` arrives with `RequiredFileOffset/RequiredLength` (and optional hints), `FileId`,
   `FileIdentity`, `PriorityHint`, `ProcessInfo`, and possibly
   `CF_CALLBACK_FETCH_DATA_FLAG_RECOVER` (see 3f) `[s3]`. The callback enqueues a
   `HydrationRequest` keyed by `TransferKey` and returns.
2. Hydration worker (semaphore 3-4) acquires the global `ThrottleGate`, then looks up the item in
   the index by `FileIdentity`/`FileId`.
3. It fetches a fresh `@microsoft.graph.downloadUrl` (`$select=id,@microsoft.graph.downloadUrl`)
   for this request; URLs are pre-authenticated and expire in roughly an hour or less, so they are
   never cached across requests and never logged `[s21]`.
4. It issues `GET downloadUrl` with `Range: bytes={offset}-{end}` and
   `HttpCompletionOption.ResponseHeadersRead`, no Authorization header `[s21]`.
   - 206: stream the body.
   - 200 (server ignored Range `[s21]`): treat as "stream from offset 0", skipping bytes before the
     required offset, still writing everything received (write-ahead is allowed).
   - 401/403/404 mid-stream: refetch downloadUrl once and resume from the first byte not yet
     transferred; second failure fails the request.
5. Streaming loop: read into a rented fixed-size buffer (1-4 MiB from a dedicated `ArrayPool`),
   call `CfExecute(TRANSFER_DATA)` for each full 4 KiB-aligned chunk (the alignment rule is in
   `CF_OPERATION_PARAMETERS`, followed by Nextcloud/ownCloud `[s8] [s22]`), return the buffer in
   `finally`. No file-sized allocation ever happens.
6. Progress: `CfReportProviderProgress(TotalBytes, CompletedBytes)` at least every 15 s while the
   transfer is alive, even with zero new bytes (resets the timer `[s8]`); Explorer shows the
   progress bar.
7. Deadline and failure: each request has a progress-stall budget (no bytes for 45 s) and the
   `ThrottleGate` reports the next allowed time. If `Retry-After` or the stall would exceed the
   budget, the worker completes the request with a failing `CompletionStatus`
   (`STATUS_CLOUD_FILE_NETWORK_UNAVAILABLE`-style, exact code to verify in spike) so Explorer shows
   an error rather than 0x800701AA `[s9]`. A request is never left pending.
8. `CANCEL_FETCH_DATA` cancels the token; the worker stops and completes with the cancelled status.
   Partially written ranges stay on disk (no rollback by the platform `[s8]`), which is fine under
   PROGRESSIVE.
9. After the burst (no hydrations for 10 s) the worker pool signals the memory hygiene step
   (section 6).
10. Memory-mapped readers and antivirus scans request the whole file even under PROGRESSIVE
    (**community-reported** `[s23]`); `ProcessInfo` is logged so scanner-driven hydration is
    visible in diagnostics, and `BLOCK_SELF_IMPLICIT_HYDRATION` keeps the engine's own I/O out.

### 3c. Delta ingestion streamed into SQLite

1. Trigger: startup, adaptive poll timer (1 min active, backing off to 15-60 min idle), daily
   safety full delta, later socket.io notification `[s16] [s17]`. Single ingest worker.
2. `GET` persisted `nextLink` (resume) or `deltaLink`, or `/me/drive/root/delta?$select=...&$top=N`
   for the first sync (`$select` is baked into the returned tokens `[s24]`; honoured `$top` to verify
   in spike).
3. Response body is deserialized as a stream (`DeserializeAsyncEnumerable` over the `value`
   array); items are applied in batches of about 500 inside one SQLite transaction: deletes first,
   upsert the rest, last occurrence of a duplicate id wins, track by `id` and `parentReference.id`
   only (`parentReference.path` is absent; renames do not re-emit descendants) `[s24]`. Consumer
   deletes omit `ctag` and `size` `[s24]`.
4. After each page commit, persist the page's `@odata.nextLink`; a crash resumes from it.
5. For items already materialised on disk (index has `fileId`): schedule a placeholder update
   (metadata only via `CfSetInSyncState`/rename/move), a tombstone for deletes (recycle bin
   semantics locally, never for a `NotInSync` file), or a conflict entry. Items not materialised
   are only index rows; Explorer sees them on the next FETCH_PLACEHOLDERS.
6. Folders are deleted locally only when empty after the whole page set is applied `[s24]`.
7. On HTTP 410 Gone: read `Location` (fresh nextLink) and the error code
   (`resyncChangesApplyDifferences` / `resyncChangesUploadDifferences`); mark the run as a resync
   and re-walk the whole feed against the index with the same streaming path (no in-RAM diff)
   `[s24]`.
8. The run finishes by storing the new `deltaLink`; the next tick is scheduled with back-off.
   Delta-with-token costs 1 resource unit `[s17]`.
9. Runs at `ThreadPriority.BelowNormal` with the same `ThrottleGate` as transfers; it never blocks
   a cfapi worker (separate channel and semaphore).

### 3d. New-file upload

Triggered by the watcher: a plain NTFS file (no reparse point) appears under the sync root and is
stable for the debounce window.

1. Reconciler creates the item row in `LocalNew` and a journal entry `Upload{localPath,
   parentGraphId, name}` in one transaction.
2. Sanitise the name against OneDrive restricted characters and case-insensitive collisions;
   surface a conflict entry rather than renaming silently (rclone/abraunegg practice `[s25]`).
3. Upload worker (semaphore 2-3) opens the file with `FileShare.Read`, computes quickXorHash while
   streaming `[s26]`, and chooses the path:
   - size <= 4 MiB: simple `PUT .../items/{parentId}:/{name}:/content?@microsoft.graph.conflictBehavior=fail`
     (PUT defaults to `replace`, so the behaviour is always explicit) `[s20]`.
   - larger: `POST createUploadSession` with body `item.@microsoft.graph.conflictBehavior=fail`,
     `item.name`, `fileSystemInfo.lastModifiedDateTime`, `fileSize` (personal only; 507 if over
     quota); `uploadUrl` is journaled; then sequential `PUT` fragments of 5-10 MiB, each a multiple
     of 320 KiB and under 60 MiB, `Content-Range` set, **no Authorization header** (can yield 401),
     read from disk into a rented buffer wrapped in `ReadOnlyMemoryContent` `[s20]`.
     createUploadSession defaults to `fail`, PUT defaults to `replace`: set it explicitly on both.
   - 202 => `nextExpectedRanges`; 416 => range already received, continue; 404 => session gone,
     restart; `GET uploadUrl` on resume returns missing ranges `[s20]`.
4. On 2xx with the `driveItem`: store `graphId`, `eTag`, `cTag`, hash, then
   `CfConvertToPlaceholder` + `CfSetInSyncState` on the local file (a new local file is a plain
   file until converted, **community-reported** FAQ `[s13]`). Verify `file.hashes.quickXorHash`
   matches; absent hash => fall back to size + second-precision timestamp `[s26]`.
5. On 409 `nameAlreadyExists` (conflictBehavior fail): create a conflict entry; the user resolves
   in Settings (v1) instead of silent overwrite.
6. For P2 edits: `If-Match: <eTag>` on every replace; 412 => write the remote version as
   `<name> (conflicted copy <date>)` and keep the local as a new upload (critique resolution).
7. Echo suppression: the uploaded item's `eTag`/`cTag` are stored so the next delta page recognises
   our own change and does not re-download.

### 3e. Delete and rename: ack locally, sync later

1. `NOTIFY_DELETE` / `NOTIFY_RENAME` arrives (blocks the user's operation until acked `[s8]`). The
   callback enqueues `{RequestKey, FileId, FileIdentity, path, targetPath, flags}` to the
   high-priority ack channel and returns.
2. Ack worker (dedicated, never shares a semaphore with network work) decides from local state
   only:
   - Rename/move inside the root: `ACK_RENAME` with success; journal `Move{graphId, newParentId,
     newName}`.
   - Move out of the root: for a dehydrated placeholder the data is not local, and acking success
     would hand the user an empty file. v1 denies the operation (`ACK_RENAME` with a failure
     status) and the tray explains; hydrated items are allowed and journaled as `Delete`. P2 adds a
     CopyHook warning. (Decision recorded here; Explorer's rendering of the denial to verify in
     spike.)
   - Delete: `ACK_DELETE` with success; journal `Delete{graphId}`. Mass-delete guard: if the
     journal would exceed N items or X% of the index in one batch, the ack still succeeds locally
     but the remote deletes are parked and sync pauses until the user confirms (critique
     resolution; rclone bisync has `--max-delete` for the same reason `[s27]`).
   - A `NotInSync` item (P2 dirty file) being deleted is acked, and the pending upload is cancelled
     with a conflict entry so nothing is lost silently.
3. Idempotency: a single user delete can raise several `NOTIFY_DELETE`s (Recycle Bin move then
   delete, per-child on folder delete, delete-on-close; **community-reported** FAQ `[s13]`).
   Handlers key on `RequestKey`/`FileId` and a journal `Delete` for an already-tombstoned id is a
   no-op.
4. `*_COMPLETION` callbacks update the index (`fileId`, new path) so the next delta page matches.
5. The sync worker executes journal entries in order: `PATCH /items/{id}` with
   `parentReference.id` / `name`, `DELETE /items/{id}` (recycle bin; `permanentDelete` is supported
   on personal `[s28]` but never used by default). Failures (404 already gone => done; 412/409 =>
   conflict entry) never surface as a frozen dialog; Explorer's move dialog finished at step 2.

### 3f. Crash recovery: journal and RECOVER flag

1. Startup order: open index -> replay journal entries with `status != done` (idempotent) ->
   USN replay from the saved cursor -> `CfConnectSyncRoot` -> resume delta from `nextLink`.
2. Registration persists across reboots; the connection does not and is re-established every
   start `[s3]`. The engine never unregisters on exit (unregistering permanently deletes unhydrated
   placeholders `[s6]`).
3. A hydration interrupted by crash or power loss comes back as `FETCH_DATA` with
   `CF_CALLBACK_FETCH_DATA_FLAG_RECOVER` `[s3]`; the worker treats it as a normal progressive request
   from the required offset (already-written ranges are reported by `CfGetPlaceholderRangeInfo`,
   to verify in spike) rather than trusting any in-memory state.
4. An upload session found in the journal is resumed via `GET uploadUrl` -> `nextExpectedRanges`
   `[s20]`; a 404 restarts it.
5. Delta ingestion resumes from the persisted `nextLink`; duplicate application is harmless by
   construction (upsert by id).
6. Acceptance: kill the engine during hydration and during delta ingestion, restart, verify no
   stuck placeholders, no lost journal entries, Explorer recovers without restart.

## 4. Per-item state machine

`localState` column; one row per Graph item (and per not-yet-uploaded local file with a
temporary negative id until Graph assigns one).

| State | Meaning |
|---|---|
| `RemoteOnly` | Known from delta, no placeholder on disk yet (parent folder not yet enumerated). |
| `Placeholder` | Dehydrated placeholder on disk, `IN_SYNC`. |
| `Hydrating` | At least one FETCH_DATA in flight. |
| `Hydrated` | Full content on disk, `IN_SYNC`; `Pinned` is a flag, not a state. |
| `LocalNew` | Plain NTFS file detected by the watcher, upload journaled, not yet sent. |
| `Uploading` | Upload (simple or session) in progress; `uploadUrl` journaled. |
| `PendingRemoteOp` | Local delete/rename acked; `Move`/`Delete` journal entry not yet confirmed by Graph. |
| `Dirty` (P2) | Local edit not yet uploaded; `NOT_IN_SYNC`; never dehydrated. |
| `Conflict` | Needs the user: 409/412, name collision, unsupported item, parked mass delete. |
| `Tombstone` | Deleted remotely or locally; row kept until the matching delta/ack is observed, then purged. |

Transitions (trigger -> result):

- delta upsert, parent not enumerated -> `RemoteOnly`
- FETCH_PLACEHOLDERS page created -> `RemoteOnly` -> `Placeholder`
- FETCH_DATA enqueued -> `Placeholder`/`Hydrated` -> `Hydrating`; completed (full) -> `Hydrated`;
  completed (partial) or cancelled -> `Placeholder` (ranges tracked by the platform, not by us)
- `FILE_ATTRIBUTE_UNPINNED` observed or Storage Sense -> `Hydrated` -> dehydrate -> `Placeholder`;
  refused if `Dirty`
- watcher: new plain file stable -> `LocalNew`; worker starts -> `Uploading`; 2xx + convert ->
  `Hydrated` (in sync); 409/412 -> `Conflict`
- NOTIFY_DELETE acked -> `PendingRemoteOp` (kind Delete); Graph 2xx/404 -> `Tombstone` -> purge
- NOTIFY_RENAME acked -> `PendingRemoteOp` (kind Move); Graph 2xx -> previous content state
- delta `deleted` facet for a `Placeholder`/`Hydrated` item -> local delete to Recycle Bin ->
  `Tombstone`; for `Dirty`/`LocalNew`/`Uploading` -> `Conflict` (never delete unsynced data)
- delta change (eTag differs) for `Hydrated` not `Dirty` -> metadata update; if `cTag` differs ->
  dehydrate-on-next-open or re-hydrate lazily (v1: mark `Placeholder` by dehydrating when no handle
  is open; otherwise defer)
- any Graph 429/503 -> no state change; the `ThrottleGate` holds the worker
- journal replay at startup -> re-enters `Uploading`/`PendingRemoteOp` without re-deciding

Invariants (checked in tests): a `Dirty` or `LocalNew` item is never dehydrated or deleted by a
remote event; every `PendingRemoteOp`/`Uploading` row has a journal entry; a `Tombstone` row has
no pending cfapi request.

## 5. Concurrency and back-pressure

- One bounded `Channel<T>` per work kind, each drained by a fixed number of workers:
  `hydration` (cap 256, 3-4 workers), `enumeration` (cap 64, 1-2), `ack` (cap 1024, 1, highest
  priority, never waits on network), `localChange` (cap 4096, 1 reconciler), `delta` (single
  worker, no queue), `remoteOps` (journal-backed, 2-3 uploads + 1 metadata worker).
- Callback-side policy on a full channel: fail the cfapi request immediately with a status (user
  sees an error, Explorer stays alive). Nothing on the callback thread ever waits.
- `SemaphoreSlim` caps network concurrency; the `HttpClient` has `MaxConnectionsPerServer` 4-8
  `[s29]`.
- `ThrottleGate`: one process-wide "not before" timestamp fed by `Retry-After`; every Graph call
  awaits it; while it is in the future, pending cfapi requests whose remaining budget is shorter
  are failed proactively.
- Per-request deadline object (`RequestBudget`): created in the callback, carries start time,
  last progress time, `CancellationTokenSource`; the supervisor sweeps them. Budgets: enumeration
  30 s total, hydration 45 s without progress (progress reported every 15 s), ack 2 s
  (local-only).
- Priority: `PriorityHint` from the callback orders the hydration channel (Explorer foreground
  opens before background pins). Pin ("Always keep on this device") of a big folder produces many
  FETCH_DATAs with no cancel callback (**community-reported** `[s13]`); the engine's own tokens
  cancel them on pause.
- Thread pool: Native AOT on Windows uses the Windows thread pool by default; `SetMinThreads` is a
  no-op there `[s30]`. The spike measures idle thread count under both settings before deciding on
  `UseWindowsThreadPool`.

## 6. Memory model: why idle memory is independent of item count

- No in-RAM tree. The only per-item storage is NTFS (placeholders exist only for enumerated
  folders) and SQLite on disk. Lookups are indexed queries; the SQLite page cache is bounded by
  `PRAGMA cache_size` (value chosen in spike), so a 500k-item index costs disk, not RAM.
- Streaming everywhere: delta pages deserialized as a stream in batches, downloads copied through
  fixed-size pooled buffers into `CfExecute`, uploads read from `FileStream` chunk by chunk. No
  `ReadAsByteArrayAsync`, no `MemoryStream` of a file.
- Bounded queues mean bounded in-flight state: at most (channel capacity x small struct) +
  (workers x buffer size) is ever live, independent of drive size.
- Runtime configuration (runtimeconfig): workstation GC, `System.GC.Concurrent=false`,
  `System.GC.ConserveMemory` 5-7, `System.GC.RegionSize` 1 MB (runtimeconfig setting since .NET 10),
  `System.GC.RetainVM=false`, optional `System.GC.HeapHardLimit` (fails loudly instead of eating the
  machine) `[s31]`.
- Post-burst hygiene: when the last transfer of a burst finishes, dispose streams, return buffers,
  drop caches, then `GC.Collect(GC.MaxGeneration, GCCollectionMode.Aggressive)`; .NET 10+ ages freed
  UOH regions over two gen2 GCs, so a second aggressive collect a few seconds later may be needed,
  verified via `GC.GetGCMemoryInfo().TotalCommittedBytes` `[s32]`. No periodic collections while
  idle; working-set trimming APIs only move pages to standby and are not used as a metric `[s33]`.
- Networking: `SocketsHttpHandler.PooledConnectionIdleTimeout` 20-30 s and
  `PooledConnectionLifetime` ~5 min so idle TLS connections and their buffers go away soon after a
  sync `[s29]`.
- Idle discipline: no timers under one minute while idle, so the thread pool drains `[s4]`.
- Binary: Native AOT, `OptimizationPreference=Size`, `InvariantGlobalization`,
  `UseSystemResourceKeys`, `EventSourceSupport=false`, `MetricsSupport=false`,
  `HttpActivityPropagationSupport=false`, `Http3Support=false`; `DebuggerSupport` stays true to
  keep the separate .pdb for crash dumps `[s34]`.
- Acceptance: idle Private Bytes under a fixed budget regardless of item count (target < 30 MB
  with a 500k-item index); after a 10 GB hydration burst commit returns within 10 MB of idle inside
  60 s; peak during 500k-item ingestion stays flat. Published AOT numbers exist only for ASP.NET
  apps (about 23 MB AOT vs 40 MB JIT working set on Windows), so the real baseline is measured in P0
  step 2 `[s35]`.

## 7. Safety rules

Carried verbatim in intent from the plan's "Safety rules baked in from day one" and
"Non-negotiable: never hang Explorer, never balloon memory"; enforced in code review and tests.

Non-negotiable responsiveness rules:

1. No I/O inside a cfapi callback: validate, enqueue to a bounded channel, return in microseconds.
   All network, disk and database work happens on workers that complete via `CfExecute`.
2. Every pending request has a watchdog with a deadline well under 60 s; progress is reported at
   least every 15 s while work continues; a request that cannot progress is completed with a
   failure status. A stuck request is never left pending.
3. Delete and rename acks are never delayed by the network: acknowledged from local state, remote
   operation journaled; Explorer's dialog finishes in local-move time; failures surface later as a
   conflict entry.
4. FETCH_PLACEHOLDERS answers from the local index only, in batches, with pagination; opening a
   50k-child folder never calls Graph.
5. Bounded everything: fixed concurrency (hydration 3-4, uploads 2-3, delta 1), bounded queues
   with back-pressure, fixed-size pooled buffers returned immediately, `HeapHardLimit` so a bug
   fails loudly. Memory is independent of item count by construction.
6. Idempotent and crash-safe: journal before execute, replay after crash; double delete callbacks
   and duplicate delta entries are harmless; RECOVER-flagged hydrations are handled.
7. Never block Explorer with our own handles: placeholder updates through `CfOpenFileWithOplock`;
   the engine breaks its own oplocks immediately when asked.
8. Debounce local change storms in the watcher, off the callback path, with hash/eTag comparison
   before any upload.
9. Self-protection: the supervisor monitors callback latency, queue depth and commit; over budget
   => fail the request, log, and if necessary disconnect/reconnect or restart cleanly.

Data-safety rules:

- `If-Match: eTag` on every content replace; explicit `@microsoft.graph.conflictBehavior` on every
  write; conflict copies instead of overwrites.
- Mass-delete threshold pauses sync and asks the user.
- Never dehydrate or remotely delete a `NotInSync`/`Dirty`/`LocalNew` file.
- Remote deletes go to the OneDrive recycle bin only; `permanentDelete` is never the default.
- Uninstall flow: disconnect -> hydrate-all prompt or explicit warning -> `CfUnregisterSyncRoot`
  (it permanently deletes unhydrated placeholders `[s6]`) -> remove folder; `Unregister` is the
  unpackaged app's responsibility `[s36]`.
- Refuse to start while OneDrive.exe is linked to the same account (NoDrive is a replacement, not
  an add-on; two engines on one account double every file and fight over changes).
- Never place the sync root at a drive root; NTFS only; no overlapping sync roots
  (`CfGetSyncRootInfoByPath` check before registering) `[s1] [s6]`.
- Never `CfUnregisterSyncRoot` on normal exit; always `CfDisconnectSyncRoot` on shutdown.

### 8.1 Start-up guard and adoption (ADR-0008)

Start-up order in `Engine/Program`: single-instance mutex -> load `config.json` -> **OneDrive guard** -> auth -> register/connect -> workers. The guard is read-only and unelevated: read `HKCU\Software\Microsoft\OneDrive\Accounts\Personal` (`UserFolder`, `UserEmail`), enumerate `HKLM\...\Explorer\SyncRootManager\OneDrive!<SID>!Personal*`, and call `CfGetSyncRootInfoByPath` on the configured root. Any hit on a linked personal account, or a foreign provider owning the root, means: tray balloon with unlink instructions, exit code 3, no connect. Business-only OneDrive is allowed.

Adoption is a worker (`Core/Adopt`) that runs after the first full delta pass, behind the same bounded channels as everything else: walk the root breadth-first, batch 512 entries, join against the index by path; match on size + UTC mtime (1 s) -> `CfConvertToPlaceholder` + `CfSetInSyncState`, enqueue lazy quickXorHash verification; mismatch -> rename to `<name> (local copy YYYY-MM-DD)` and create the cloud placeholder; unknown -> upload-new pipeline. Adopted-but-unverified files carry `AdoptedUnverified` in the index and are never dehydrated until the hash pass clears them. Known-folder redirection is detected with `SHGetKnownFolderPath(id, 0)` vs `SHGetKnownFolderPath(id, KF_FLAG_DEFAULT_PATH | KF_FLAG_NOT_PARENT_RELATIVE)` for Desktop, Documents, Pictures, Screenshots and Camera Roll (registry `User Shell Folders` read only as a diagnostic, never `Shell Folders`); a redirected folder under the root aborts adoption with a tray message that links to the migration steps. Native "Folder backup" support is P2 (`IKnownFolderManager::Redirect` with copy + delete-source + UI, folder pinned by default, reversible), see `research/known-folder-move.md`.

## 9. Known platform pitfalls designed around

| Pitfall | Status of evidence | Design response |
|---|---|---|
| Fixed, non-configurable 60 s callback timeout; 0x800701AA in Explorer means an unanswered callback | Timeout documented `[s8]`; interpretation **community-reported** `[s9]` | Section 5 budgets; progress every 15 s; fail with status before the platform does. |
| After a FETCH_PLACEHOLDERS timeout Explorer may stop calling back for that folder until restart | **community-reported** `[s9]` | Enumeration from index only; 30 s budget; timeouts are bugs. |
| `NOTIFY_DEHYDRATE` not raised for Explorer "Free up space" | **community-reported**, reproduced by Microsoft External Staff `[s11]` | Watch `FILE_ATTRIBUTE_UNPINNED`; dehydrate ourselves. |
| `CfDehydratePlaceholder` documented only on an archived page | Documented gap `[s12]` | Still exported and in Win32Metadata; verify in spike; `AUTO_DEHYDRATION_ALLOWED` lets Windows do part of the work. |
| `CfUpdatePlaceholder` heap corruption on 24H2/25H2 | **community-reported**, open since Nov 2024 `[s10]` | Prefer `CfSetInSyncState`/`CfSetPinState`; repro in P0 step 4 before using it. |
| Memory-mapped reads and antivirus force full hydration under PROGRESSIVE | **community-reported** `[s23]`; `BLOCK_SELF_IMPLICIT_HYDRATION` exists for AV `[s3]` | Bounded hydration pool, chunked transfers, `ProcessInfo` logging. |
| `CfUnregisterSyncRoot` permanently deletes unhydrated placeholders | Documented `[s6]` | Never on exit; uninstall flow hydrates or warns. |
| Provider not running => 0x8007016A on every online-only file | Documented behaviour `[s3]` | Autostart, single instance, Task Scheduler restart, supervisor. |
| Session-0 hydration blocked | **community-reported**: reproduced by a Microsoft Q&A responder in 2022; GitHub issue #245 open with no Microsoft reply `[s2]` | Per-user interactive process, never a service. |
| Sync root must be indexed for correct Status column | Only a CloudMirror code comment, **community-reported** `[s42]` | Add `%USERPROFILE%\NoDrive` to the crawl scope; compare in spike. |
| Explorer holds handles on ancestor folders of an open subfolder | **community-reported** `[s43]` | Rename/move failures surface as conflicts, never block. |
| Folder-level "Free up space" disabled unless a descendant is pinned | **community-reported** `[s44]` | Tray fallback actions. |
| Hydration verbs moved into a per-provider flyout on Insider builds | Windows Insider blog `[s7]` | Tray fallback; verify on the target build. |
| Replace-on-save strips the reparse point and identity blob | **community-reported** FAQ `[s13]` | Watcher treats result as a local edit; re-convert after upload (P2). |
| Multiple `NOTIFY_DELETE` per user delete | **community-reported** FAQ `[s13]` | Idempotent acks keyed on `RequestKey`/`FileId`. |
| Unpackaged `Register` showing nav-pane node and Status on the target build | **community-reported** `[s45]`; `Unregister` docs assume unpackaged apps `[s36]` | P0 step 3 confirms; fallback `CfRegisterSyncRoot` + registry. |
| CsWinRT projection on net11.0-windows under AOT undocumented | CsWinRT 2.3.1 documents .NET 9/10 only `[s46]` | P0 step 3; fallback to Win32-only registration or a non-AOT helper exe. |
| Graph downloadUrl may ignore Range (200 full body) and expires quickly | Documented `[s21]` | Section 3b handles 200 as write-ahead from offset 0; URL fetched per request. |
| 429/503 Retry-After longer than the cfapi budget | Documented `[s17]` + plan gap | `ThrottleGate` fails pending requests proactively with a status. |
| Newly consented personal apps reported to get 403 serviceReadOnly | **community-reported**, no Microsoft reply `[s47]` | P0 step 1 tests a fresh app and account on day one. |
| tempauth URL retirement 2027-04-01, consumer scope unclear | Message Center item `[s18]` | `IContentTransfer` seam. |
| `sharedWithMe`/`recent` stop returning data after Nov 2026 | Documented deprecation `[s48]` | No "Shared with me" UI; rely on delta `remoteItem` entries. |
