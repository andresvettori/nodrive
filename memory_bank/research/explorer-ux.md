# Research: File Explorer UX for a cfapi provider

Verified knowledge base from the 2026-11-13 research pass (`ux` topic report + adversarial fact-checker verdict, plus the UX-relevant gaps from the completeness critique). Overall reliability of the underlying report was rated **high**; where the report and the fact-checker disagreed, the fact-checker's correction appears here. Evidence legend: **verified** (primary source linked), **community-reported** (Microsoft Q&A moderators, forums, third-party press, GitHub issues), **to verify in spike** (P0 task on the Windows 11 PC). Platform mechanics (callbacks, policies, bugs) live in `research/cfapi.md`; Graph endpoints in `research/graph-onedrive.md`; this file is only about what the user sees in Explorer and how NoDrive gets it.

Why this matters for NoDrive: the whole point of the cfapi route is that **explorer.exe renders the UI and NoDrive stays headless**. The user's OneDrive.exe pain (Explorer hangs, move dialogs stuck at "0 files remaining", ~4 GB RAM on an 8 GB PC) is the failure mode of a provider that blocks inside callbacks or keeps its tree in RAM. Every UX feature below is evaluated against two axes: does it keep Explorer responsive, and does it add resident memory. Responsiveness outranks features.

## 1. What Explorer gives a cfapi provider for free

All from Microsoft's "Build a Cloud Sync Engine" page (updated 2025-11-18), https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine, unless noted. Once a sync root is registered:

- **Navigation-pane node**: "Registering a sync root with the cloud files API causes that sync root (with an icon and custom name) to appear in File Explorer's navigation pane." Icon and name come from `StorageProviderSyncRootInfo.IconResource` (`path,index`) and `DisplayNameResource` (any `SHLoadIndirectString`-acceptable string). Roots "can be created either as individual top-level entries, or as children of a parent grouping" (`ShowSiblingsAsGroup`). Reference: https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovidersyncrootinfo
  - Caveat: that the node appears when registering from an **unpackaged** process is community-reported (Tenshu PR #6, 2026-11-10, checked "by eye": https://github.com/B3nedikt/Tenshu/pull/6). **To verify in spike** (P0 step 3) on the target build; it is a kill criterion.
- **Status column state icons**: "standardized, automatic hydration state icons shown in File Explorer and on the Windows desktop ... Replaces legacy icon overlay Shell extensions". Users know them from OneDrive: blue cloud outline = online-only, green check = locally available, solid green circle with white check = always available (pinned). Labels: https://support.microsoft.com/en-us/office/save-disk-space-with-onedrive-files-on-demand-for-windows-0e6860d3-d9f3-4971-b321-7092438fb38e
  - Caveat: the CloudMirror sample comments that items outside the Windows Search indexer scope do not return the expected property values, so the Status column can be wrong for an un-indexed root. The only source is that code comment quoted in a 2020 community Q&A answer (https://learn.microsoft.com/en-us/answers/questions/96456/why-sync-root-folder-should-be-indexed-(cfapi)); treat as a strong practical hint, **to verify in spike** by comparing icons inside vs outside an indexed folder. Plan: add `%USERPROFILE%\NoDrive` to the crawl scope programmatically (CloudMirror does this via `ISearchCrawlScopeManager`).
- **Built-in hydration verbs**: "Registering a sync root with the cloud files API automatically provides several verbs (menu entries) in File Explorer's context menu that let the user control the hydration state of their file." Labels users see: "Always keep on this device" and "Free up space" (OneDrive support page above). On Windows 11 the 2021 dev blog says provider commands sit "next to the Shell commands to hydrate or dehydrate the file" in the modern menu: https://blogs.windows.com/windowsdeveloper/2021/07/19/extending-the-context-menu-and-share-dialog-in-windows-11/
  - Caveat: their placement is changing in Insider builds (section 4). **To verify in spike** on the target build; keep a tray-menu fallback.
  - Known limitation (community-reported): folder-level "Free up space" stays disabled unless some descendant is PINNED; a vendor moderator called it "might be a design choice" (details and link in `research/cfapi.md`, pitfall 7).
- **Hydration progress and toasts**: "In a copy engine dialog window. Inline progress is shown next to the file in File Explorer. If the file is not opened at the user's specific instruction, a toast notification is shown." The filter "automatically tracks the progress of hydrations" from the `TRANSFER_DATA` ranges NoDrive writes via `CfExecute`; call `CfReportProviderProgress` when downloading to a temp location first, which also resets "the 60 second timeout period corresponding to the CF_CALLBACK_TYPE_FETCH_DATA callback": https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfreportproviderprogress
- **Consent UI for background hydration**: non-user-initiated hydration (an app or scanner touching a placeholder) raises an interactive toast, and users can block an app under Settings > Automatic file downloads. No code needed.
- **Transparency**: placeholders are ~1 KB reparse points; any Win32/UWP/console app opens them through normal `CreateFile`; Open/Save dialogs, double-click, drag from Explorer all work. Three file states: placeholder (online-only), full (hydrated), pinned full. Minimum OS Windows 10 1709 (build 16299); NTFS only (cldflt.sys).
- **Windows Storage Sense dehydration**: with `HydrationPolicyModifier.AutoDehydrationAllowed`, Windows itself can free space without the provider (cfapi fact-checker; see `research/cfapi.md`).

The CloudMirror sample's registration (MIT, C++) is the reference shape: `HydrationPolicy`, `PopulationPolicy`, `InSyncPolicy`, `ShowSiblingsAsGroup(false)`, `IconResource`, `DisplayNameResource`, `RecycleBinUri`, `Context` blob, then `StorageProviderSyncRootManager::Register(info)`: https://raw.githubusercontent.com/microsoft/Windows-classic-samples/main/Samples/CloudMirror/CloudMirror/CloudProviderRegistrar.cpp. NoDrive deliberately departs from its `HydrationPolicy Full` / `PopulationPolicy AlwaysFull` / creation-time InSync choices (section 8).

## 2. Registry-based shell integration without package identity

**Verified** against Nextcloud's shipping unpackaged client (GPL, read-only reference) and Microsoft docs. Nextcloud desktop registers with `CfRegisterSyncRoot(..., CF_REGISTER_FLAG_UPDATE)` (Hydration FULL / Population PARTIAL / InSync PRESERVE_INSYNC_FOR_SYNC_ENGINE) and then writes registry values itself:

- `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\SyncRootManager\<provider!SID!account!alias>`: `Flags` (REG_DWORD, 34 normally; 2 suppresses the cfapi context-menu verbs; the meaning of the other bits is undocumented), `DisplayNameResource`, `IconResource` (`<exe>,0`), `UserSyncRoots\<SID>` = root path, `CustomStateHandler` = CLSID, `ThumbnailProvider` = CLSID, `NamespaceCLSID` = nav-pane CLSID. Source: https://raw.githubusercontent.com/nextcloud/desktop/master/src/libsync/vfs/cfapi/cfapiwrapper.cpp
- Nav-pane node, HKCU only (`navigationpanehelper.cpp`): `Software\Classes\CLSID\{guid}` with `DefaultIcon`, `System.IsPinnedToNameSpaceTree=1`, `SortOrderIndex=0x41`, `InProcServer32=%systemroot%\system32\shell32.dll`, `Instance\CLSID={0E5AAE11-A475-4c5b-AB00-C66DE400274E}`, `Instance\InitPropertyBag` (`Attributes=0x11`, `TargetFolderPath`), `ShellFolder` (`FolderValueFlags=0x28`, `Attributes=0xF080004D`), plus `Desktop\NameSpace\{guid}` and `HideDesktopIcons\NewStartPanel`, mirrored under `Wow6432Node`. Source: https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/navigationpanehelper.cpp. This is the same 12-step recipe as Microsoft's "Integrate a Cloud Storage Provider" page, which uses `reg.exe` on HKCU and never mentions packaging: https://learn.microsoft.com/en-us/windows/win32/shell/integrate-cloud-storage
- `StorageProviderSyncRootManager.Register` performs the SyncRootManager writes for you and has **no documented elevation or identity requirement**; its sibling `Unregister` doc says "Desktop apps that are not packaged using MSIX must call this method when uninstalled", Microsoft's clearest acknowledgment that unpackaged providers are a supported configuration. https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovidersyncrootmanager.register
- Risk if using `CfRegisterSyncRoot` directly from an unelevated per-user install: Nextcloud treats a failed HKLM write as non-fatal (logs, deletes the key tree, continues without shell integration), so nav-pane node, Status branding and handler CLSIDs can **silently fail**. The ACL of the `SyncRootManager` key for standard users could not be verified from any primary source. Conclusion: NoDrive registers through `StorageProviderSyncRootManager.Register` (plan default); `CfRegisterSyncRoot` + registry is only the fallback if the CsWinRT/.NET 11 AOT path fails, and then the HKLM write result must be checked and surfaced.

### Handler-by-handler evidence

All handlers below are **COM local servers (out-of-process)**: they run in NoDrive's process, never in explorer.exe. Good for Explorer stability (a crash never takes Explorer down), but the engine must be running or COM-launchable (`HKCU\Software\Classes\CLSID\{..}\LocalServer32`) or the feature silently disappears. Every handler call is also a latency path Explorer waits on: answer from local cache only, never from Graph.

| Handler | Registered via (no identity) | Evidence quality | Notes |
|---|---|---|---|
| `CustomStateHandler` (`IStorageProviderItemPropertySource`) | `SyncRootManager` registry value (Nextcloud ships it) or `desktop3:CustomStateHandler` manifest | **Verified**: Nextcloud source above; API: https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.istorageprovideritempropertysource | Alternative with no handler at all: declare `StorageProviderItemPropertyDefinitions` at registration and push per-item `StorageProviderItemProperties.SetAsync(IStorageItem, ...)` (Id, Value, IconResource); Explorer shows extra icons/column. https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovideritemproperties.setasync |
| `ThumbnailProvider` | `SyncRootManager` registry value (Nextcloud ships it) or `desktop3:ThumbnailProviderHandler` | **Verified**: Nextcloud source; CloudMirror `ShellServices/ThumbnailProvider` demonstrates it: https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/cloudmirror-sample | Explorer will not hydrate an online-only placeholder to make its own thumbnail, so without this handler online-only photos show generic icons (critique gap; community-reported: https://learn.microsoft.com/en-gb/answers/questions/977606/how-to-set-thumbnail-for-a-hydrated-placeholder-fi). Graph `/thumbnails` makes it cheap (section 8). |
| `StatusUISourceFactory` (`IStorageProviderStatusUISourceFactory`) | Docs: "register the implementation class in the app manifest **or registry**" | **Verified text, unverified in practice**: https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.istorageproviderstatusuisourcefactory. The related `IStorageProviderKnownFolderSyncInfoSourceFactory` documents an explicit unpackaged path under `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StorageProvider`, "consistent with the existing mechanism for unpackaged provider registration" (cfapi fact-checker; see `research/cfapi.md`, package-identity table). No shipping unpackaged provider using it was found. **To verify in spike/P2.** | Requires 23H2+ with feature detection (section 4). The claim that it is "mandatory" for the Windows 11 header flyout comes from a vendor moderator (WICLOUD Corporation, 2025-11-10) on the Q&A FAQ, **community-reported**: https://learn.microsoft.com/en-us/answers/questions/2288103/cloud-file-api-faq |
| `ShareHandler` (out-of-proc `IExplorerCommand`) | `SyncRootManager` registry value "to the CLSID of their COM local server object", invoked when the user picks Share on a cloud file | **Verified text** (sync-engine page); Windows 11 21H2+; no shipping unpackaged example found. **To verify.** | The only no-identity way to put a NoDrive command ("Copy link") into Explorer's modern menu surface. |
| `CopyHook` (`IStorageProviderCopyHook`) | `SyncRootManager` registry value, build 19624+ | **Verified text** (sync-engine page); no shipping unpackaged example found. **To verify.** | Lets NoDrive warn before a move out of the root (which becomes remote delete + local plain copy that must hydrate first; critique delete-safety gap). Must answer instantly or it becomes a new way to stall move dialogs. |
| `SearchHandlerFactory` | `SyncRootManager` registry value | **Verified text**, but only on Windows 11 24H2 Copilot+ PCs / AI-enabled Cloud PCs | Not a general option; ignore. |

The raw report's mention of a "StorageProviderGetContentInfoForPath thumbnail API" was wrong; it is this interface, not thumbnails. |
| `ExtendedPropertyHandler`, `BannersHandler`, `DesktopIconOverlayHandlers` | `desktop3:CloudFiles` manifest only | **No documented registry equivalent** (open question) | https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-desktop3-cloudfiles |

Microsoft's caveat that cfapi sync engines "are designed to use the Desktop Bridge as an implementation requirement" (same sync-engine page) describes the manifest route; it is not a runtime check, and the Q&A statement that "a background console application (no UI) can use the Cloud Files API" is **community-reported** (vendor moderator).

## 3. What requires package identity

Microsoft's identity-required list (updated 2026-10-03): "Custom context menu extensions" (Windows 11 modern menu), "Startup tasks", "Manifest-based file type and protocol associations", "Share target", "Background tasks", "App services", "Push notifications (WNS)", "Windows AI APIs". Explicitly not required: "The Windows App SDK app notifications APIs (local app notifications) work in both packaged and unpackaged apps and do not require package identity." https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/modernize-packaged-apps

### Windows 11 modern context menu (`IExplorerCommand`)

**Verified** (doc updated 2026-07-16): https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer
- "Windows 11 apps extend the modern File Explorer context menu by implementing IExplorerCommand and registering the command with app identity. This applies to packaged desktop apps and to unpackaged Win32 apps that use a sparse package."
- "A native DLL implements one or more COM classes that expose IExplorerCommand"; "C++ is the usual choice because the command runs in the Shell integration path"; "The DLL architecture must match the File Explorer architecture that loads it". Registration: `com:SurrogateServer` (ThreadingModel STA) + `desktop4:FileExplorerContextMenus` / `desktop5:ItemType Type="*" | "Directory" | "Directory\Background"` with `desktop5:Verb Clsid`. Keep `GetTitle/GetIcon/GetState` fast. Multiple verbs are grouped into a flyout with app attribution; Q&A reports only one submenu level (**community-reported**: https://learn.microsoft.com/en-us/answers/questions/1120506/how-to-create-a-shell-extension-using-iexplorercom.html).
- Classic `IContextMenu` extensions land under "Show more options"; "Shift-F10 or the keyboard menu key will also load the Windows 10 context menu" (2021 dev blog above).
- Nextcloud's legacy in-proc `NCContextMenu` (`IShellExtInit` + `IContextMenu`, https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/windows/NCContextMenu/NCContextMenu.h) has crashed explorer.exe (0xc0000005, `confirmedbug`): https://github.com/nextcloud/desktop/issues/6566. An in-proc shell DLL in C# (CLR inside explorer.exe, or a Native AOT DLL with hand-rolled COM exports) is fragile and off the table. **Rule: NoDrive never ships in-proc code in explorer.exe.**

### Sparse package ("package with external location") if ever needed (P3)

**Verified** (doc updated 2026-10-03): https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps (overview: https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps-overview)
- Windows 10 2004 / build 19041+. Manifest: `<uap10:AllowExternalContent>true</uap10:AllowExternalContent>`, `<Application uap10:TrustLevel="mediumIL" uap10:RuntimeBehavior="win32App">`, capabilities `runFullTrust` + `unvirtualizedResources`, `ProcessorArchitecture="neutral"`, `TargetDeviceFamily MinVersion="10.0.19041.0"`. Build: `MakeAppx.exe pack /o /d <dir> /nv /p pkg.msix`. The exe needs a fusion manifest `<msix publisher= packageName= applicationId=/>` matching `Identity`.
- Signing: "must be signed with a certificate that is trusted on the target computer". Dev: self-signed cert imported with `Import-Certificate ... -CertStoreLocation Cert:\CurrentUser\TrustedPeople` (no admin; `LocalMachine\TrustedPeople` needs elevation), otherwise `CERT_E_UNTRUSTEDROOT (0x800B0109)`. "A production certificate from an IT Department or a service like Azure Trusted Signing will be required to register the package on end user computers."
- Register per user: `Add-AppxPackage -Path pkg.msix -ExternalLocation <installDir>` or `PackageManager.AddPackageByUriAsync(uri, new AddPackageOptions { ExternalLocationUri })`.
- Gotchas (troubleshooting table): `0x80073CF9` same version already registered (bump `Version` every rebuild or `Remove-AppxPackage` first), `0x80073D54` manifest/fusion mismatch, `0x80073CF6`, and "Identity absent at runtime (no error)" when `ExternalLocation` differs from the actual run directory.
- Unsigned packages (doc updated 2026-04-15): Windows 11 only, Publisher must carry `OID.2.25.311729368913984317654407730594956997722=1`, `Add-AppxPackage -AllowUnsigned`, "Don't use this feature to distribute your app widely", and a package with executable content "must be installed for all users", i.e. admin. Whether an identity-only sparse package (no binaries inside, but an `<Application Executable=...>` entry) counts as non-executable is undocumented; assume admin is required. https://learn.microsoft.com/en-us/windows/msix/package/unsigned-package
- Cost/benefit: a few hours of one-time setup plus ongoing certificate and version churn, and the only prizes are modern-menu entries, a manifest `StartupTask` (HKCU `Run` does the job unpackaged) and share-target. If it is ever done, the menu DLL is a thin native forwarder that posts to the engine process and does nothing else.

## 4. Windows version notes

NoDrive floor per the plan: Windows 11 24H2 with the August 2025 cumulative update or later (cldflt.sys fix for CVE-2025-50170, see `research/cfapi.md`); Windows 10 22H2 under ESU shares the cfapi baseline but is untested. Note the fact-checker's correction: Windows 10 is not "unsupported" (consumer ESU reportedly extended to Oct 2027, **community-reported**; commercial ESU to 2028: https://learn.microsoft.com/en-us/windows/whats-new/extended-security-updates); Windows 11-only is an effort decision, not a lifecycle one.

- **Status-UI flyout needs 23H2+ and feature detection.** The `IStorageProviderStatusUISourceFactory` reference lists "Device family: Windows 11 Insider Preview (introduced in 10.0.23504.0)", API contract `Windows.Storage.Provider.CloudFilesContract` v7.0. Build 23504 is a 2023 Insider build later than the 22H2 RTM build 22621, so the interface is not guaranteed on bare 22H2; plan for 23H2 (22631)+ and gate with `ApiInformation.IsTypePresent`. https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.istorageproviderstatusuisourcefactory
- **Hydration verbs moving into a per-provider flyout.** Insider Build 26220.7271 (KB5070307, Dev + Beta, 2025-11-21): "We've moved cloud provider options, like Always Keep on this Device and Free Up Space" into the relevant cloud provider flyout, alongside a new "Manage file" flyout. No Microsoft statement that this reached GA was found; **verified Insider note, GA status to verify in spike.** https://blogs.windows.com/windows-insider/2025/11/21/announcing-windows-11-insider-preview-build-26100-7271-dev-beta-channels/
- **User-customisable context menu (KB5127936).** Optional preview for 25H2/26H2 (builds 26200.9818 / 26300.9818, 2026-10-28) lets users choose which app extensions and commands appear and how they are ordered; a user can hide the hydration verbs entirely. **Community-reported** (third-party press): https://www.bleepingcomputer.com/news/microsoft/windows-11-kb5127936-update-released-with-41-changes-and-fixes/
  - Consequence for NoDrive: "rely entirely on built-in verbs" is not safe. v1 ships tray-menu fallbacks ("Free up space in folder...", "Keep folder offline") that call `CfSetPinState` / `CfDehydratePlaceholder` directly (the latter is documented only on an archived page; see `research/cfapi.md`, pitfall 12).
- **File Explorer Home integration for cloud providers.** Insider 26220.6760 (2025-09-29) added "StorageProvider APIs for cloud providers to integrate with File Explorer Home"; Insider 26220.7070 (2025-11-07) said "We are temporarily turning off the integration supporting the StorageProvider APIs for cloud providers". A potential v2+ surface; currently unstable, do not plan on it. https://blogs.windows.com/windows-insider/2025/09/29/announcing-windows-11-insider-preview-build-26220.6760-dev-channel/ and https://blogs.windows.com/windows-insider/2025/11/07/announcing-windows-11-insider-preview-build-26220-7070-dev-beta-channels/
- **Search handler** (`IStorageProviderSearchHandlerFactory`): Windows 11 24H2 Copilot+ PCs or AI-enabled Cloud PCs only (sync-engine page). Not a general option.
- **Other minimums** (sync-engine page): CopyHook build 19624+; ShareHandler Windows 11 21H2+; cfapi itself 1709+.
- **Windows 11 context menu for a cfapi provider** (2021 dev blog): provider commands are placed next to the hydrate/dehydrate Shell commands; "Show more options" loads the Windows 10 menu as-is.

## 5. Notifications

- **cfapi provides the toasts that matter**: hydration progress toast for non-user-initiated hydration and the "Automatic file downloads" consent UI, with zero code (section 1). v1 needs nothing else.
- **Windows App SDK `AppNotificationManager` works unpackaged** (no identity): "For unpackaged apps, Register() automatically sets up the COM server registration that allows Windows to launch your app when a notification is clicked. You don't need to configure COM activation or an AUMID manually." Call `Register()` before `AppInstance.GetCurrent().GetActivatedEventArgs()`. "Notifications for elevated (admin) apps are not currently supported." The .NET page's prerequisites assume WPF/WinForms; a separate console/headless page exists. https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-dotnet and https://learn.microsoft.com/en-us/WINDOWS/APPS/develop/notifications/app-notifications/app-notifications-console
  - Cost: an unpackaged app must bootstrap the Windows App SDK runtime (`<WindowsPackageType>None</WindowsPackageType>` auto-calls `MddBootstrapInitialize2`), which needs the framework package installed (bootstrapper can prompt via `WindowsAppSDKBootstrapAutoInitializeOptions_OnNoMatch_ShowUI`) or a self-contained deployment, and starts the Dynamic Dependency Lifetime Manager: extra DLLs mapped into the **idle** engine process. https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/use-windows-app-sdk-run-time
  - Current version: **2.6.5 (2026-11-02)**, not the 2.4.0 the raw report cited. Release table: 2.0.1 (2026-04-29), 2.2.0 (2026-06-09, added `Microsoft.Windows.Storage.ApplicationData.GetForUnpackaged()`), 2.4.0 (2026-08-13), 2.6.4 (2026-10-27), 2.6.5. https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0
  - Windows App SDK supports Native AOT since 1.6 (requires CsWinRT 2.1.1+, `Microsoft.Windows.SDK.NET.Ref` 10.0.22621.38+): https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-6
- **Legacy AUMID route (no Windows App SDK)** is still documented: Start-menu shortcut carrying an `AppUserModelID` and a COM activator CLSID, `ToastNotificationManager.CreateToastNotifier(aumid)`, `INotificationActivationCallback` COM server (Microsoft.Toolkit.Uwp.Notifications helpers). Only the en-us `send-local-toast` URL 404s; the sibling page exists: https://learn.microsoft.com/en-us/windows/apps/design/shell/tiles-and-notifications/send-local-toast-other-apps. If NoDrive ever needs its own toasts (conflict found, sign-in expired, mass-delete paused), this route avoids the Windows App SDK runtime in the resident process; it is **to verify** on current Windows 11.
- Decision: no NoDrive-originated toasts in v1. Errors surface in the tray icon state/tooltip and the conflict list; cfapi handles hydration UX. Re-evaluate in P2 alongside the StatusUI flyout, which is the natural home for sync errors.

## 6. Custom Explorer-like client: why it was rejected

A standalone browser window (Avalonia 12 / WinUI 3 / WPF) was evaluated and is **strictly worse on both axes the user cares about**:

- **Transparency**: only placeholders make files appear as ordinary files to every app (Open/Save dialogs, double-click, drag from Explorer, command line). A custom client must re-implement "open / edit / auto-upload" (download to a cache dir, `ShellExecute`, watch, debounce, upload), which is exactly odrive's `.cloud` / `.cloudf` stub-file model ("Double clicking on any placeholder file will transform it into a regular file"): fake extensions, no Status column, no dialog transparency. https://docs.odrive.com/docs/sync-your-odrive
- **Drag-out of online-only items is the hard part**: Avalonia 12 (GA 2026-04-07, .NET 8+ only, docs recommend .NET 10) replaced `IDataObject` with `DataTransfer`/`DataTransferItem`; a drag starts with `DragDrop.DoDragDropAsync(PointerPressedEventArgs, IDataTransfer, DragDropEffects)` and `DataTransferItem.CreateFile(IStorageItem)` (`DataFormat.File` is the only multi-item format on Windows). That produces a `CF_HDROP` of existing local paths, so dragging an online-only item to Explorer forces a synchronous download before the drop. The deferred alternative (`CFSTR_FILEDESCRIPTOR` / `CFSTR_FILECONTENTS`) is exposed by none of Avalonia, WPF or WinForms. https://docs.avaloniaui.net/docs/input-interaction/drag-and-drop , https://docs.avaloniaui.net/docs/avalonia12-breaking-changes , https://avaloniaui.net/blog/avalonia-12
- **Memory**: a custom client must keep a renderer/XAML stack resident while the user works; a cfapi provider is headless and explorer.exe (already running) does the UI. No credible published idle working-set comparison of WinUI 3 vs WPF vs Avalonia exists; the only nearby data point is unrelated (Windows Latest measured explorer.exe at ~32 MB vs ~67 MB with preloading: https://www.windowslatest.com/2025/11/28/tested-windows-11s-faster-file-explorer-preloaded-is-still-slower-than-windows-10-and-uses-additional-ram). **To measure in spike** for the Settings process only.
- **Effort**: a file browser with search, previews, drag-and-drop, context menus and conflict UI is a product in itself and still would not fix the Explorer experience.
- Market signal: Mountain Duck 5 moved its Windows product onto cfapi "Integrated" mode in 2025 (section 7) precisely to get out of the custom-mount business.

Where a custom UI does belong: the on-demand **Settings** process (sign-in, folder choice, pause, conflicts), which exits when closed so no UI framework sits in the idle footprint. v1 can be tray menu + browser sign-in + JSON config; Avalonia 12 or WinUI 3 (both AOT-capable) later.

## 7. Commercial references

- **Mountain Duck 5** (proprietary; its Cyberduck core is GPL-3.0 Java, inspiration only). 5.0.0 (2025-08-19) added the "Integrated" connect mode using the Cloud Files API on Windows: "The mount is not seen as a remote volume by applications but as a regular folder on disk. No device driver installation or network mount required"; UI is a tray icon plus Explorer context entries; its older "Smart Synchronization" mode used a kernel driver. 5.3.1 (2026-07-03) upgraded the Windows runtime to .NET 10; latest 5.4.0 (2026-11-05). This is the UX benchmark for NoDrive (Online Only / Always keep on this device / Free up space, overlay states, inline progress), with the "pseudo-locking" caveat noted in `research/oss` material. https://blog.cyberduck.io/2025/08/12/integrated-connect-mode/ , https://docs.cyberduck.io/mountainduck/interface/ , https://mountainduck.io/changelog/
- **odrive**: `.cloud` / `.cloudf` stub files instead of cfapi; the anti-pattern NoDrive avoids. https://docs.odrive.com/docs/sync-your-odrive
- **Nextcloud desktop**: tray app + cfapi VFS + classic in-proc shell extension (GPL-2.0-or-later). The most battle-tested cfapi code and the source of most risk controls below; read for protocol and registry layout, never copy (NoDrive is MIT).
- **Insync** (selective sync, no on-demand placeholders) and **Air Explorer** (two-pane transfer manager) are not relevant models.

## 8. Recommended v1 UX and v2 candidates

Decisions here follow the approved plan; where the raw `ux` report differed (it suggested `PopulationPolicy AlwaysFull`, `HydrationPolicy Full` as an option, and MSAL), the plan's choices win: PARTIAL population is mandatory at 500k items, PROGRESSIVE hydration is lighter and documented (Graph `Range` on `downloadUrl` returns 206, may fall back to 200; see `research/graph-onedrive.md`), and auth is hand-rolled PKCE. Effective hydration policy is max(app policy, provider policy), so registering FULL would force full-file download on first byte for every app (fact-checker).

### v1 (P1): the minimum that feels like OneDrive, with zero resident UI

- One sync root at `%USERPROFILE%\NoDrive` (never a drive root, NTFS), registered with `StorageProviderSyncRootManager.Register`: `HydrationPolicy Progressive` + `AutoDehydrationAllowed`, `PopulationPolicy Partial`, `InSyncPolicy FileLastWriteTime | DirectoryLastWriteTime`, `ShowSiblingsAsGroup false`, branded `IconResource` / `DisplayNameResource`, `RecycleBinUri` to the OneDrive web recycle bin. Add the root to the Search crawl scope. **Verify in spike** whether `Register` creates the HKCU nav-pane CLSID keys or NoDrive must write them itself (Nextcloud writes them).
- Explorer surfaces used: nav-pane node, Status column, built-in verbs, inline/dialog/toast progress. Nothing custom in explorer.exe.
- Tray icon (`Shell_NotifyIcon` via CsWin32, re-added on `TaskbarCreated`) with: Pause/Resume, Open folder, Open OneDrive on the web, Free up space in folder..., Keep folder offline, Sign in/Sign out (system browser), Quit. Tray tooltip/icon state shows idle / syncing / paused / error (sign-in needed, mass-delete paused).
- Callbacks implemented: `FETCH_DATA`, `CANCEL_FETCH_DATA`, `FETCH_PLACEHOLDERS` (from the local index only), `NOTIFY_DELETE` / `NOTIFY_RENAME` (+ completions), acked immediately from local state.
- Deliberately skipped in v1: thumbnails (online-only photos show generic icons; see v2 item 1), custom states, StatusUI flyout, custom context menu, NoDrive toasts, conflict UI beyond the conflict-copy file itself, "Shared with me" (endpoints deprecated Nov 2026), Personal Vault and OneNote package items (shown as unsupported, not as placeholders).

### v2 candidates, ranked by UX value per effort (none needs package identity)

1. **ThumbnailProvider COM local server** backed by Graph `/thumbnails` (sizes small=96, medium=176, large=800 on the longest side, `*Square` variants, custom `c300x400` / `c300x400_crop`; `/thumbnails/{id}/{size}/content` 302s to a cache-safe URL; `?$expand=thumbnails` on children works on personal OneDrive, not Business): serve `large`, cache on disk, never block Explorer waiting on Graph (return "no thumbnail" and refresh asynchronously). Promote to late v1 if photos matter. https://learn.microsoft.com/en-us/graph/api/driveitem-list-thumbnails
2. **StatusUISourceFactory** for the Windows 11 header flyout: sync state, quota, errors, Pause command. 23H2+, `ApiInformation.IsTypePresent` gate, WinRT COM-server authoring under Native AOT on .NET 11 unverified (section 9).
3. **ShareHandler** (out-of-proc `IExplorerCommand`) to put "Copy link" behind Explorer's native Share entry.
4. **CustomStateHandler / `StorageProviderItemProperties`** for a "Shared" badge or an error badge on conflicted items.
5. **CopyHook** to warn on moving files out of the root (pairs with the delete-safety policy in `systemPatterns.md`).
6. File Explorer Home integration once Microsoft re-enables the StorageProvider APIs (section 4).
7. (P3, identity) Sparse package + native forwarder DLL for modern context-menu entries. Only if 1-6 prove insufficient.

## 9. Risk controls learned from Nextcloud and cfapiSync

These map one-to-one onto the user's OneDrive.exe symptoms and are hard rules (see `bestPractices.md` and `systemPatterns.md` for the enforcement mechanics).

- **Never block in a cfapi callback.** Return in microseconds after enqueueing; do network, disk and database work on workers; complete via `CfExecute` asynchronously; Explorer (and every app touching the folder) freezes otherwise. Nextcloud 33.0.x-35.0.0 shipped a regression with 30-40 s freezes of Explorer, Word and Firefox on write operations in very large VFS folders (one report: ~860 GB / 360k files, i.e. the user's scale). The fix is **not developer-confirmed**: the forum title says "fixed with 35.0.1" but the thread body has no 35.0.1 test report, the related issue nextcloud/desktop#10150 remained open, and the 35.0.1 notes (2026-10-29) only list "[stable-35.0] Bugfix/mgallien/windows vfs more reliable" (#11091) and "improve new folder in windows vfs handling" (#11060). Lesson stands; root cause undiagnosed in public, so callback latency is an **unquantified risk** that NoDrive measures itself (p99 < 5 ms acceptance test). https://help.nextcloud.com/t/windows-11-explorer-freez-with-nextcloud-client-33-0-0-to-35-0-0-fixed-with-35-0-1-update/243345 , https://github.com/nextcloud/desktop/releases/tag/v35.0.1
- **Ack deletes and renames instantly from local state** and queue the remote operation; a delayed `NOTIFY_RENAME`/`NOTIFY_DELETE` ack is exactly the stuck "0 files remaining" move dialog. Expect double `NOTIFY_DELETE` (Recycle Bin, replace-on-save) and make it idempotent (`research/cfapi.md`, pitfall 9).
- **Respect the 60 s deadline with a margin**: `CfReportProviderProgress` at least every 15 s while a hydration is alive; when progress is impossible (429 `Retry-After` longer than the remaining budget, expired `downloadUrl`, offline) complete the request with a failing `CompletionStatus` so Explorer shows an error instead of hanging; the moderator-suggested `CF_OPERATION_ACK_DATA_FLAG_CANCELED` does not exist.
- **Debounce Office storms**: Word/Excel save sequences (temp file, rename, delete, replace-on-save that strips the reparse point) must be debounced 2-5 s off the callback path with hash/eTag comparison before any upload; the cfapiSync author notes "Word and Excel drives me crazy" and lists Office temp-file deletes as a known issue: https://github.com/styletronix/cfapiSync
- **Never unregister on normal exit**: register with `CF_REGISTER_FLAG_UPDATE` semantics (Nextcloud) and keep the registration across restarts (CloudMirror comment); `CfUnregisterSyncRoot` permanently deletes unhydrated placeholders, so it belongs only in the uninstall flow after a hydrate-or-warn step. Always `CfDisconnectSyncRoot` on shutdown (`WM_QUERYENDSESSION`).
- **Never place the sync root at a drive root** (cfapi limitation reported in Nextcloud PR #3290 via Microsoft Q&A, **community-reported**); NTFS only; no nested/overlapping roots (`Register` fail-fasts).
- **Keep Explorer out of the blast radius**: every shell handler is an out-of-proc COM local server; no in-proc DLL (Nextcloud #6566 crash). A NoDrive crash must only ever cost a failed hydration (0x8007016A while down), never an Explorer restart; Task Scheduler restart-on-failure brings the engine back.
- **Don't fight your own process**: Nextcloud/ownCloud reject `FETCH_DATA` originating from their own process to avoid deadlocks; NoDrive connects with `CF_CONNECT_FLAG_REQUIRE_PROCESS_INFO | BLOCK_SELF_IMPLICIT_HYDRATION` and never opens placeholder data through the filesystem itself (uses `CfOpenFileWithOplock` / `CfExecute`).
- **Keep the verbs**: if the `CfRegisterSyncRoot` fallback is used, `Flags` must be the default (34), not 2, or the built-in verbs vanish.
- **Test with Defender and a third-party AV**, and with apps that memory-map files (Photos, Office): both force hydration behind the user's back and both must stay inside the hydration concurrency cap.
- **Memory stays flat by construction**: the only thing the UX layer may cache in RAM is the tray state; placeholders, index and thumbnails live on disk.

## Navigation pane placement (measured 2026-11-15, Windows 11 PC)
Windows creates the sidebar entry itself from the sync root (value NamespaceCLSID under SyncRootManager; SortOrderIndex 66, icon from IconResource). OneDrive has the same SortOrderIndex but sits in the top group (Home, Gallery, OneDrive) because its CLSID carries TargetKnownFolder={a52bba46-e9e1-435f-b3d9-28daa648c0f6} (the OneDrive known folder). A third party cannot use it without taking over that Windows folder, so NoDrive stays in the lower group. A custom CLSID of our own only creates a duplicate entry (tested, removed).
