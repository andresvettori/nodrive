1. Upload sessions: how it persists and resumes them, how it handles 409/416 on a fragment, the ghost/empty item an abandoned session leaves, session expiry. (Our Wi-Fi cut bug, see `activeContext.md` 2026-11-17/18.)
2. eTag / cTag behaviour after upload (OneDrive re-processing media changes the eTag), and how it decides "changed in the cloud" before a delete or update.
3. Delta quirks: duplicates, out-of-order items, items without hashes, 410 resync, deleted items without metadata, the consumer/business differences it documents.
4. Name and path rules (invalid characters, case collisions, trailing dots) and how it reports them.
5. Throttling (429 / Retry-After) and its own back-off, plus how it uses webhooks/websocket notifications versus polling.
6. Its known-issues and troubleshooting documents (a catalogue of API surprises).

## Findings
### 2026-11-18, upload sessions (subagent read of the master source; line numbers may drift, issues not searched)
- **Same design as ours:** saves the session as a JSON file (url, expiry, ranges, local path, size, mtime, target ids), re-saved after every fragment; on startup it resumes only if size and mtime match exactly and a GET on uploadUrl still answers with `nextExpectedRanges`; empty ranges = already complete; a discarded session is cancelled with DELETE uploadUrl. No hash check before resuming.
- **Confirms our ghost theory:** a code comment says an aborted session on OneDrive Personal can appear as a zero-byte remote placeholder, which is why they cancel explicitly. They do NOT detect or delete an existing zero-byte item and do not handle nameAlreadyExists; they send conflictBehavior=replace on sessions (we use fail to never overwrite, hence our ghost cleanup).
- Fragment errors: 404 -> new session; 403 (tempauth expired, independent of expirationDateTime) -> new session from 0; 416 -> re-PUT same offset (no status query; ours asks the session first); 409 -> no special handling; others one retry. Retry waits: 429/408 Retry-After, 5xx flat 30 s, others exponential up to 120 s; retry limit about a year (ours is bounded).
- Fragment size default 10 MiB (10-60 MiB, multiple of 320 KiB); ours is 5 MiB.
- Completion: the final response is the DriveItem; they compare size and quickXorHash with the local hash computed while streaming; mismatch only warns. No recovery found for a timeout on the LAST fragment (ours: hash adoption).
- Personal quirks: session creation sends fileSystemInfo.lastModifiedDateTime (whole seconds) so the server keeps the local mtime; simple uploads cannot carry it, so the local mtime is set to the server's; zero-byte files always use a simple PUT (OneDrive/onedrive-api-docs issue 53); `If-Match` on session creation was once disabled because the eTag changes after creation (412 then 416 on the last fragment), now sent with one retry.
- **Done in NoDrive from this:** fragment 403/404/401 forgets the saved session and retries with a new one; diagnostic hash check after the first 50 uploads of a run (log "hash check ok / MISMATCH") to validate our quickXorHash against OneDrive's.
- **Also done (2026-11-18):** `fileSystemInfo.lastModifiedDateTime` (whole seconds) is sent when a session is created so the cloud keeps our mtime; fragments are 10 MiB (buffer above the ArrayPool limit, transient: re-measure memory during a large upload); the session expiry is saved and an expired session is replaced without a status request. 75 tests. Not yet verified against the real service.

### 2026-11-18, eTag / cTag / delta / names (subagent read of sync.d, onedrive.d, util.d and docs; partial audit of a 19.5k-line file)
- **eTag is their only change marker; cTag is stored but never compared.** A changed eTag only says "look closer": content equality is decided by size, then quickXorHash (then sha256, else size alone). They keep the applied-content baseline (hash, size) separate from the eTag, so a metadata-only eTag change is not a content change. No explicit note found that media post-processing moves the eTag; they avoid the problem by comparing content.
- **If-Match:** sent on metadata PATCH (rename/move/timestamp); **NOT sent on DELETE** (commented out with a TODO: "always fails with 412"); sent on createUploadSession for modified files, with comments saying the eTag moves once a session starts (last fragment 412 then 416): behaviour unsettled. 412 on a move: re-read the live eTag, retry up to 3 times without eTag; 409: delete the destination first.
- Personal items sometimes have no quickXorHash (sha1/sha256 may be returned instead); deleted items carry a bogus all-zero hash (never trust hashes on deletes); zero-size files are tolerated.
- Timestamps: UTC, fractional seconds dropped; local change = mtime differs (seconds) then hash compared only if mtime differs; hash equal = just fix the timestamp. After a simple upload the server stamps its own mtime and they set the local mtime to it.
- Delta: 410 -> drop the link, full enumeration authoritative for presence; the new deltaLink is persisted only after the whole run commits (we persist the nextLink page by page for resume, and the final deltaLink at the end); transactions of 500. Duplicates/out-of-order handling not found in the part read: test ours (idempotent upserts, defer children until the parent exists).
- Names rejected by OneDrive (util.d): `.lock`, `desktop.ini`, CON/PRN/AUX/NUL/COM0-9/LPT0-9, names starting `~$`, containing `_vti_`, leading/trailing whitespace, trailing dot, `<>:"|?*/\`, root-level `forms` folder; case-insensitive. A 409 on folder creation is treated as a race (read the existing folder). Case-only collisions are not uploaded.
- **Done in NoDrive from this (2026-11-18):** (a) an edit whose content equals the cloud copy (same size, equal quickXorHash, file <= 512 MiB) is marked in sync, not uploaded; (b) a delete that gets 412 is re-verified against the live item (size + hash) and then retried with the fresh eTag and, if that also fails, without If-Match; (c) upload ignore list gains `.lock`, `_vti_` and leading-space names (the root-level `forms` folder is NOT handled yet).
- **To check on the PC / open:** a large-file EDIT (> 4 MiB, session with If-Match) may fail at the last fragment (412/416); our 412 path now compares the cloud hash before making a conflict copy, but test it. Verify delete with If-Match on Personal for ordinary files.
