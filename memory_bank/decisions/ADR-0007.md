# ADR-0007: Lazy population (PopulationPolicy PARTIAL + FETCH_PLACEHOLDERS from the index) and PROGRESSIVE hydration for a 500k-item drive

## Status

Accepted 2026-11-13

## Context

The user's OneDrive had 400k+ items and has ~200k today. On an 8 GB PC, OneDrive.exe consumed almost 4 GB with many files, Explorer hung and became unresponsive, and move dialogs stuck at "0 files remaining" after the folder had already moved. NoDrive is therefore designed for 500k items with hard requirements: never block Explorer, idle memory independent of item count, no dialog ever left stuck. The two cfapi policies that decide this are the population policy (how placeholders come into existence) and the hydration policy (how file content is fetched).

### Evidence

- `CfRegisterSyncRoot` / `StorageProviderSyncRootInfo` offer `PopulationPolicy` ALWAYS_FULL (the provider pre-creates every placeholder) or PARTIAL (the platform calls `FETCH_PLACEHOLDERS` when a directory is first enumerated), and `HydrationPolicy` PARTIAL / PROGRESSIVE / FULL / ALWAYS_FULL with modifiers (`AUTO_DEHYDRATION_ALLOWED`, `VALIDATION_REQUIRED`, `STREAMING_ALLOWED`). `FETCH_PLACEHOLDERS` is required unless population is ALWAYS_FULL; `FETCH_DATA` is required unless hydration is ALWAYS_FULL. Source: https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfregistersyncroot , https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_callback_type
- With ALWAYS_FULL population, the initial delta enumeration must create a placeholder (one `CfCreatePlaceholders` entry and one MFT record) for every item in the drive: hundreds of thousands of filesystem operations before the drive is usable, on the very call path (`HsmpOpCreatePlaceholders`) that had a 2025 kernel fix. The research critic recommends PARTIAL for large drives and ALWAYS_FULL only under ~50k items. Source: https://starlabs.sg/advisories/25/25-50170/ ; critic resolution in the research output.
- Every callback has a fixed 60 s deadline (documented in the `CF_CALLBACK_TYPE` remarks: https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_callback_type ; the 0x800701AA interpretation is community-reported: https://learn.microsoft.com/en-us/answers/questions/2288103/cloud-file-api-faq ); `FETCH_PLACEHOLDERS` must therefore never wait on the network. The delta feed from `/me/drive/root/delta` is the only complete enumeration and is already streamed into the local index (ADR-0005), so the index can answer `FETCH_PLACEHOLDERS` for any folder from disk. Source: https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0
- Effective hydration policy is the maximum of the app's and the provider's; registering FULL forces a whole-file download on first byte access for every application, which conflicts with "as little as possible" for large media. PROGRESSIVE requires handling random-offset `FETCH_DATA` requests.
- Graph supports PROGRESSIVE: `Range` on `@microsoft.graph.downloadUrl` returns 206 with `Content-Range`, but "if the range can't be generated the Range header may be ignored and an HTTP 200 response would be returned with the full contents"; download URLs expire in about an hour and "might expire within minutes". Source: https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0 , https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0
- Memory-mapped reads (`CreateFileMapping`) and antivirus on-access scans force full hydration regardless of PROGRESSIVE (community-reported: https://learn.microsoft.com/en-us/answers/questions/2103011/(bug-report)-cfapi-createfilemapping-causes-full-p ); `CF_CONNECT_FLAG_BLOCK_SELF_IMPLICIT_HYDRATION` exists because AV scans provider activity on non-hydrated placeholders. Source: https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfconnectsyncroot
- Nextcloud 33.0-35.0 froze Explorer, Word and Firefox for 30-40 s on write operations in very large VFS folders (one report: ~860 GB / 360k files); the related issue nextcloud/desktop#10150 remained open. Slow work on the callback path at scale is the exact failure mode to design out. Community-reported: https://github.com/nextcloud/desktop/issues/10150
- The ux and cfapi researchers initially recommended ALWAYS_FULL population and FULL hydration "for simplicity"; the critic flagged the contradiction and resolved it as PROGRESSIVE hydration plus population chosen by drive size. With a 200k-500k item target the choice is PARTIAL.

## Decision

Register the sync root with `PopulationPolicy = PARTIAL`, `HydrationPolicy = PROGRESSIVE`, `HydrationPolicyModifier = AUTO_DEHYDRATION_ALLOWED`, `InSyncPolicy = FileLastWriteTime | DirectoryLastWriteTime`, and connect with `CF_CONNECT_FLAG_REQUIRE_PROCESS_INFO | CF_CONNECT_FLAG_BLOCK_SELF_IMPLICIT_HYDRATION`. Placeholders are created lazily, when Explorer (or any app) first enumerates a folder, by `FETCH_PLACEHOLDERS` answered exclusively from the SQLite index in pages; never from live Graph calls. File content is fetched on demand in ranges via `FETCH_DATA` with `Range` requests to `downloadUrl`, tolerating a 200 full-body reply.

Rules that follow:

- `FETCH_PLACEHOLDERS`: the callback validates and enqueues; a worker reads the folder's children from the index in batches (for example 1,000 entries per `CfExecute TRANSFER_PLACEHOLDERS`), reports progress, and completes. A 30k-child folder must finish well inside 60 s from the index alone (P0 acceptance test). If the index has no data for the folder yet (initial delta still running), complete with what is known and let the delta ingestion fill the rest; never block on the network.
- Initial delta ingestion runs at low priority, streamed page by page into SQLite (ADR-0005), with `$top` as large as consumer OneDrive honours (to verify in spike), resumable via the persisted `nextLink`, and never creates placeholders itself; folders already enumerated by Explorer receive new children through `CfCreatePlaceholders` in small batches off the callback path.
- `FETCH_DATA`: fixed concurrency (3-4), fixed-size pooled buffers (1-4 MiB) streamed from the HTTP response into `CfExecute TRANSFER_DATA` in 4 KiB-aligned ranges, `CfReportProviderProgress` at least every 15 s, `CANCEL_FETCH_DATA` honoured via `CancellationToken`, failure completed explicitly (no `CF_OPERATION_ACK_DATA_FLAG_CANCELED` exists) when `Retry-After` exceeds the remaining budget, the URL expired twice, or the network is down. Explorer shows an error; it never waits.
- `downloadUrl` fetched per hydration and refreshed on 401/403; after a 200-on-Range, treat the stream as the full file and either write it all (small file) or re-issue the range request later; verify `quickXorHash` when the whole file is present.
- Never dehydrate a file that is not InSync; self-dehydration on `FILE_ATTRIBUTE_UNPINNED` (because `NOTIFY_DEHYDRATE` does not fire for "Free up space") goes through the same InSync gate.
- Memory is independent of item count by construction: no tree in RAM, no placeholder pre-creation, bounded queues and buffers, `HeapHardLimit` as the loud failure.
- The P0 scale test (fake Graph server emitting 500k items) measures first-sync time, index size and peak/idle memory before any Explorer work.

## Consequences

### Positive

- The drive is usable seconds after sign-in: the root folder shows as soon as its children are indexed, no 500k-placeholder creation storm.
- Opening a folder never calls Graph on Explorer's behalf; folder opens stay fast even with tens of thousands of children.
- PROGRESSIVE lets media players and viewers read the first bytes without downloading whole files, and keeps hydration buffers fixed-size.
- Both `FETCH_PLACEHOLDERS` and `FETCH_DATA` run on the same queue/watchdog machinery, so the "never hang Explorer" acceptance tests cover the whole provider.

### Negative

- Two mandatory callbacks instead of one; `FETCH_PLACEHOLDERS` paging, per-folder population state and "folder enumerated before delta finished" are extra state to get right.
- Windows Search and the Status column only know about populated folders; drive-wide search results appear as folders get enumerated or as delta ingestion creates placeholders in already-populated folders.
- PROGRESSIVE adds random-offset range handling and the 200-on-Range fallback; apps that memory-map or AV scans still trigger full hydration.
- Many small `Range` requests can cost more Graph calls than one full download; mitigated by a minimum range size (for example 1-4 MiB) and read-ahead.

### Revisit when

- The P0 spike shows `FETCH_PLACEHOLDERS` from the index cannot meet the 60 s deadline for large folders, or the per-folder population state proves unreliable (then ALWAYS_FULL population for drives under ~50k items as a configurable mode).
- `downloadUrl` stops honouring `Range` reliably, or MC1492958 (tempauth URL retirement, 2027-04-01) reaches consumer OneDrive without range support on bearer `GET /content` (then FULL hydration with streaming into a temp file).
- Microsoft changes population semantics or the Insider "File Explorer Home" / per-provider flyout work alters how enumeration is triggered.
