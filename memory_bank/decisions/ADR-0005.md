# ADR-0005: SQLite via the system `winsqlite3.dll` as the disk-backed index and journal

## Status

Accepted 2026-11-13

## Context

NoDrive is designed for a 500k-item drive (the user's drive had 400k+ items, now ~200k) and the engine must never hold the item tree in RAM: idle memory must be independent of item count. It needs a persistent, id-keyed item index (graphId, parentId, name, size, eTag, cTag, quickXorHash, NTFS FileId, USN, sync state, deltaLink) plus a crash-safe journal of pending remote mutations, queried by graphId, parentId (for `FETCH_PLACEHOLDERS` batches) and FileId (for local change events).

### Evidence

- Lazy `FETCH_PLACEHOLDERS` must answer from local data only, in batches, within the 60 s callback deadline, for folders with tens of thousands of children (plan rule 4). Delta ingestion streams 1,000-2,500 pages of 200 items into the store in transactions with bounded buffers and must be resumable. A real database with indexes and transactions fits; an in-memory tree does not.
- rclone's memory is dominated by in-RAM directory trees (0.5-1 KB per object), the behaviour NoDrive must avoid; abraunegg/onedrive uses SQLite as its reconciliation baseline keyed by (driveId, id). Sources: https://rclone.org/faq/ , https://github.com/abraunegg/onedrive/blob/master/docs/client-architecture.md
- Windows 10/11 ship `winsqlite3.dll` in System32. Microsoft documents `SQLitePCLRaw.bundle_winsqlite3` ("Uses winsqlite3.dll, the system SQLite library on Windows 10") and `SQLitePCLRaw.provider.winsqlite3` with `Microsoft.Data.Sqlite.Core`: zero native payload in our publish output. Source: https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/custom-versions
- Microsoft.Data.Sqlite's default bundle (`bundle_e_sqlite3`) ships a ~1-2 MB native `e_sqlite3.dll` and has had trim warnings (efcore #29725, closed not-planned). Its Native AOT status is not officially stated; under AOT the provider must be set explicitly (`SQLitePCL.raw.SetProvider(new SQLite3Provider_winsqlite3())`) instead of relying on `Batteries.Init()` reflection. Source: https://github.com/dotnet/efcore/issues/29725
- MirrorPulse/CfSharp (Apache-2.0) already pairs a cfapi provider with an SQLite state store, a useful shape reference. Source: https://github.com/MirrorPulse/CfSharp

### Alternatives

1. Microsoft.Data.Sqlite with `bundle_e_sqlite3`: known-good ADO.NET surface but adds a native DLL to ship and update, and the trim-warning history.
2. Raw `LibraryImport` P/Invoke of ~15 `sqlite3_*` functions from `winsqlite3.dll` (open, prepare, bind, step, column, finalize, exec, busy_timeout, changes, last_insert_rowid, errmsg, close): no managed dependency at all, AOT-trivial, but we write the thin wrapper and lose ADO.NET ergonomics.
3. Custom append-only binary index: smallest footprint, but we would re-implement indexes, transactions, crash recovery and compaction for 500k rows, the riskiest part of a sync engine.

## Decision

The index and the mutation journal live in one SQLite database file at `%LOCALAPPDATA%\NoDrive\index.db`, opened through the system `winsqlite3.dll`. Primary binding: `Microsoft.Data.Sqlite.Core` + `SQLitePCLRaw.provider.winsqlite3` with the provider set explicitly at startup; the P0 spike verifies a warning-free `PublishAot`. If the spike shows AOT friction, switch to alternative 2 (raw `LibraryImport` of `winsqlite3.dll`) behind the same internal `IIndexStore` interface; alternative 3 (custom binary store) is the last resort, only if `winsqlite3.dll` itself cannot be driven from AOT code (plan fallback order: Microsoft.Data.Sqlite.Core, raw P/Invoke, custom store). The engine never materialises the tree in memory: every query is bounded (paged `FETCH_PLACEHOLDERS`, batched delta upserts).

Rules that follow:

- `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, a busy timeout, a single writer connection owned by the index actor, read connections for `FETCH_PLACEHOLDERS` workers; never open the database from a cfapi callback thread.
- Schema: `items(graphId PK, parentId, name, kind, size, eTag, cTag, quickXorHash, lastModified, fileId, usn, state, pin)`, indexes on `(parentId, name)` and `fileId`; `journal(seq PK, op, graphId, payload, createdAt, attempts)`; `meta(key, value)` for `deltaLink`, `nextLink`, schema version, USN cursor.
- Delta pages are applied in one transaction per page (deletes first, upserts after, last occurrence wins); the `nextLink` is persisted in the same transaction so ingestion is resumable after a crash.
- Every remote mutation is written to `journal` before execution and removed after the server confirms; replay at startup.
- Store size and query latency for 500k items are measured in the P0 scale test (target: `FETCH_PLACEHOLDERS` for a 30k-child folder answered from the index well inside 60 s, in pages).
- Database file lives outside the sync root (never under `%USERPROFILE%\NoDrive`).

## Consequences

### Positive

- Idle memory independent of item count by construction; the OS page cache does the caching and gives it back under pressure.
- Transactions and WAL give crash safety for the journal and resumable ingestion for free.
- No native binary to ship or update; SQLite is already on every supported Windows build.
- Inspectable with standard SQLite tools during development and support.

### Negative

- Microsoft.Data.Sqlite AOT status is unverified; a fallback binding may be needed (bounded effort, ~15 functions).
- `winsqlite3.dll` version is whatever Windows ships; no control over SQLite features (avoid newer SQL syntax; verify `json`/`RETURNING` availability before using them). Windows-only by nature; Core tests on macOS need an alternative provider (`e_sqlite3` bundle in test projects only) or an in-memory `IIndexStore` fake.
- Disk I/O on the hot path for `FETCH_PLACEHOLDERS`; mitigated by indexes, paging and the OS cache, and measured.

### Revisit when

- The P0 spike cannot get a warning-free, working `PublishAot` with Microsoft.Data.Sqlite.Core + the winsqlite3 provider (then alternative 2).
- Measured `FETCH_PLACEHOLDERS` or delta-ingestion latency on the 500k-item fake drive misses its budget and profiling blames SQLite rather than our queries.
- Microsoft removes or deprecates `winsqlite3.dll` from Windows.

## Validation (2026-11-14, P0 steps 5-6)

`spikes/scale-500k` on the user's Windows 11 PC: Microsoft.Data.Sqlite.Core 11.0.0 + SQLitePCLRaw.provider.winsqlite3 3.0.5 over the system `winsqlite3.dll` 3.53.4 publishes Native AOT with zero IL2xxx/IL3xxx warnings and ships no native SQLite. Schema `items(id TEXT PK, parent_id, name, size, mtime, is_folder, etag, ctag, qxor, state) WITHOUT ROWID` + index `(parent_id, name)`, WAL, `synchronous=NORMAL`, `cache_size=-4096`, one transaction per delta page with the resume token in the same transaction. 500,000 rows: 154 MB (323 B/row), ingest 60.7 s, 10.3 MB private after release, 30,030-child folder listing 153 ms (first batch 3.1 ms), 16 us per point lookup, resume after interruption exact. Decision confirmed; alternatives (raw P/Invoke, custom binary store) not needed.
