# ADR-0002: .NET 11 + Native AOT for the engine, with fallback to .NET 10 LTS / trimmed JIT

## Status

Accepted 2026-11-13

## Context

The engine (`NoDrive.Engine.exe`) is an always-on, per-user process whose idle memory must be as small as possible and independent of item count. The user knows C# and has .NET 11 installed. The choice is runtime version and compilation mode.

### Evidence

- .NET 11 reached GA on 2026-11-10 as a Standard Term Support release; support ends 2028-11-14, the same date as .NET 10 LTS. .NET 8 and 9 left support the same day. Source: https://devblogs.microsoft.com/dotnet/announcing-dotnet-11/ , https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core
- Native AOT: "faster startup time and smaller memory footprints" (no figures from Microsoft). Third-party single-sample measurements for ASP.NET-style apps: ~23 MB AOT vs ~40 MB JIT working set on Windows x64 (.NET 8); 18 vs 41 MB RSS on Linux .NET 11 RC2. Nobody has published an idle number for an AOT tray/cfapi provider. Sources (secondary): https://www.thinktecture.com/en/?p=20991 , https://startdebugging.net/2026/05/native-aot-vs-readytorun-vs-jit-in-dotnet-11/
- AOT limitations: no dynamic loading, no `Reflection.Emit`, no built-in COM on Windows (use ComWrappers source generation), mandatory trimming and single file, Windows build needs VS 2022+ "Desktop development with C++", no cross-OS compilation (Windows binaries must be built on Windows). Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/ , https://learn.microsoft.com/dotnet/core/deploying/native-aot/cross-compile
- Interop story under AOT: CsWin32 0.3.371 is AOT-safe with `CsWin32RunAsBuildTask` + `DisableRuntimeMarshalling` + `allowMarshaling=false` (source: https://microsoft.github.io/CsWin32/docs/getting-started.html ); CsWinRT projections are AOT-compatible since 2.1.1 but CsWinRT 2.3.1 documents .NET 9/10 only and no CsWinRT release mentions .NET 11 (source: https://github.com/microsoft/CsWinRT/blob/master/docs/aot-trimming.md , https://github.com/microsoft/CsWinRT/releases ). No end-to-end sample of cfapi function-pointer callbacks under AOT exists.
- .NET 11 specifics: x86-64-v2 hardware baseline; Runtime Async is preview and the BCL is compiled with it on regardless of `UseRuntimeAsync`; `StackTraceSupport=false` now throws `NotSupportedException` in some APIs; new `StackTraceLineNumberSupport`; `UseOptimizedPublish` opt-in; `SocketsHttpHandler.ShouldEvictConnection` is `[Experimental("SYSLIB5008")]`. Sources: https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime , https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/sdk , https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.shouldevictconnection?view=net-11.0
- GC knobs for a small idle heap exist and are documented (workstation, non-concurrent, `ConserveMemory` 5-7, `System.GC.RegionSize` 1 MB as a runtimeconfig setting since .NET 10, optional `HeapHardLimit`, `GC.Collect(MaxGeneration, Aggressive)` after bursts) but have no published numbers for tiny heaps. Source: https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector
- WinForms and WPF are not trim/AOT compatible; they are excluded from the engine regardless of this decision. Source: https://api.github.com/repos/dotnet/wpf/issues/3811
- `IsAotCompatible` assembly metadata exists only for libraries built for .NET 10+, so `VerifyReferenceAotCompatibility` warns on most packages regardless of real behaviour. Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/

### Alternatives

- .NET 10 LTS + Native AOT: identical support end date, better-documented CsWinRT pairing, loses .NET 11's AOT interface-dispatch improvements and the new Process APIs (`StartDetached`, `KillOnParentExit`) used to launch the settings process. Source: https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries
- Framework-dependent trimmed JIT (`PublishTrimmed` + `PublishSingleFile`): removes the AOT interop risk, roughly doubles idle working set per the secondary measurements, and requires the shared runtime on the machine.

## Decision

Target `net11.0-windows10.0.26100.0` and publish the engine with Native AOT (`PublishAot=true`, `OptimizationPreference=Size`, win-x64) from day one. The P0 spike must prove the toolchain before P1 starts. If a kill criterion fires, fall back in this order: (1) .NET 10 LTS + Native AOT; (2) .NET 11 framework-dependent trimmed JIT; (3) isolate only the failing piece (for example the WinRT registration) in a separate non-AOT helper executable while the engine stays AOT.

Kill criteria (evaluated at the end of P0):

- `[UnmanagedCallersOnly]` cfapi callbacks generated via CsWin32 do not work end to end under `PublishAot` on .NET 11.
- The `net11.0-windows` CsWinRT projection does not publish under AOT and `CfRegisterSyncRoot` + registry keys does not give the nav-pane node and Status icons.
- The AOT engine's idle Private Bytes are not meaningfully below the trimmed-JIT variant on the same machine.
- IL2xxx/IL3xxx warnings from our own code cannot be driven to zero.

Rules that follow:

- Engine csproj: `PublishAot`, `OptimizationPreference=Size`, `InvariantGlobalization`, `UseSystemResourceKeys`, `EventSourceSupport=false`, `MetricsSupport=false`, `HttpActivityPropagationSupport=false`, `Http3Support=false`, `DisableRuntimeMarshalling`, `AllowUnsafeBlocks`, `DebuggerSupport=true` (symbolicated dumps), `UseRuntimeAsync=false` for our code (see techContext.md).
- runtimeconfig: `System.GC.Server=false`, `System.GC.Concurrent=false`, `System.GC.ConserveMemory` 5-7, `System.GC.RegionSize=1048576`, optional `System.GC.HeapHardLimit`.
- Only source-generated serialization (STJ), source-generated interop (CsWin32 / `LibraryImport` / `GeneratedComInterface`), no reflection-based libraries, no `Microsoft.Extensions.Hosting` (AOT status unverified).
- Every CI publish fails on any trim/AOT warning from our own code; third-party IL3058 is inventory only.
- Measure Private Bytes / Commit, never Working Set alone.

## Consequences

### Positive

- Smallest achievable idle footprint and startup time for a resident process; no shared-runtime dependency on the user's machine.
- AOT forces the hygiene (no reflection, source generators everywhere) that also keeps the binary and the dependency list small.
- STS and LTS end on the same date, so .NET 11 costs nothing in support horizon versus .NET 10.

### Negative

- Interop-heavy code on a 3-day-old runtime with no published cfapi-under-AOT sample; CsWinRT has not stated .NET 11 support.
- Runtime Async preview is baked into the BCL and cannot be fully disabled; stability risk for a v1 shipping on an STS release.
- Windows builds only on Windows (physical PC or CI); macOS is limited to planning and Core tests.
- AOT publish is slow and needs the C++ toolchain; debugging AOT-only failures is harder than JIT.
- Pre-2013 CPUs cannot run the binary (x86-64-v2 baseline).

### Revisit when

- Any kill criterion fires in P0.
- CsWinRT publishes .NET 11 support or a 3.0 GA that changes the AOT build (the TFM revision pitfall NETSDK1229: https://github.com/dotnet/sdk/discussions/54975 ).
- .NET 12 LTS ships (expected Nov 2027 from the annual cadence; not covered by the research) with a longer support window: re-target then.
- Measured idle memory of the AOT engine misses the 30 MB target and the JIT variant does not; or Runtime Async issues surface in production.
