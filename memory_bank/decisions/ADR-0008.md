# ADR-0008: Coexistence with OneDrive.exe, detection of its account and folder, and adoption of the existing sync folder

## Status

Accepted 2026-11-13 (the user confirmed on 2026-11-13 that adoption of the existing folder, epic E1b, is in v1 scope). Supersedes nothing; refines the "NoDrive replaces OneDrive.exe" decision in `projectbrief.md`.

## Context

NoDrive syncs the same personal account that the preinstalled OneDrive.exe may already be syncing. Running both engines against one account doubles disk use and makes them fight over every change (version churn, conflict copies on both sides). The user confirmed on 2026-11-13 that NoDrive is a replacement client and that they will unlink OneDrive.exe. Three questions followed: does NoDrive detect a running OneDrive, does it find the former sync folder, and can it reuse that folder instead of re-downloading everything.

Verified facts (research 2026-11-13, see `research/onedrive-client-coexistence.md`):

- **What unlink leaves on disk.** Microsoft support: "Files marked as Available on this device will remain in your computer's OneDrive folders. Files marked as Available when online will only be accessible from OneDrive on the web" (https://support.microsoft.com/en-us/office/how-to-remove-an-account-in-onedrive-72699268-9e64-45bd-b723-9a19f4512fd1). The client's own dialog says online-only files "will be removed" (quoted on Microsoft Q&A, community-reported, https://learn.microsoft.com/en-us/answers/questions/5083385/your-onedrive-files-will-stop-syncing-locally-avai). This matches `CfUnregisterSyncRoot` semantics exactly: hydrated placeholders revert to normal files, unhydrated ones are permanently deleted (https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfunregistersyncroot). So after unlink the folder contains only ordinary files, all of them locally available copies of cloud items (or local-only files that never uploaded).
- **Account and folder identification.** `HKCU\Software\Microsoft\OneDrive\Accounts\Personal` exists while a consumer account is linked, with `UserFolder` (sync root path), `UserEmail`, `UserName` (community-verified by several independent tools; Microsoft publishes no key for sync status, https://learn.microsoft.com/en-au/answers/questions/1665743/any-registry-key-to-determine-sync-status-of-onedr). A `cid` value is probable but unverified; do not depend on it. Environment variables `OneDrive`, `OneDriveConsumer`, `OneDriveCommercial` exist but are undocumented and can go stale; treat as hints only.
- **Authoritative sync-root check.** `HKLM\Software\Microsoft\Windows\CurrentVersion\Explorer\SyncRootManager\<id>` with id `OneDrive!<SID>!Personal` and `UserSyncRoots\<SID>` = path (https://learn.microsoft.com/en-us/windows/win32/shell/integrate-cloud-storage, id example `OneDrive!S-1-1234!Personal` at https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovidersyncrootinfo.id). Readable by standard users. `CfGetSyncRootInfoByPath` fails for a path that is not under any sync root and otherwise returns `ProviderName`/`ProviderStatus` (https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetsyncrootinfobypath). Sync roots may not overlap, so NoDrive cannot register on a folder that is still OneDrive's root.
- **Process.** OneDrive.exe runs per-user from `%LOCALAPPDATA%\Microsoft\OneDrive\` or per-machine from `%ProgramFiles%\Microsoft OneDrive\` (https://learn.microsoft.com/en-us/sharepoint/per-machine-installation); autostart via `HKCU\...\Run\OneDrive` with `/background`. Windows re-provisions OneDrive for new users (`OneDriveSetup.exe /thfirstsetup`, community-reported) and feature updates can bring it back; the Windows policy `DisableFileSyncNGSC=1` under `HKLM\Software\Policies\Microsoft\Windows\OneDrive` stops it on Pro/Enterprise (https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-system#disableonedrivefilesync); Home support is community-reported only.
- A business account (`Accounts\Business1`) in the same OneDrive.exe syncs a different drive to a different folder and does not conflict with NoDrive.

## Decision

1. **Detection at every start.** NoDrive reads `Accounts\Personal` (UserFolder, UserEmail) and enumerates `SyncRootManager` for ids starting with `OneDrive!<current SID>!Personal`. If a personal account is linked, or the chosen sync root is under an existing OneDrive sync root (`CfGetSyncRootInfoByPath` succeeds with a foreign provider), NoDrive does not connect: it shows a tray balloon with the unlink instructions and exits with a non-zero code. A running OneDrive.exe with no personal account (business only, or not signed in) is allowed. Detection never kills or modifies OneDrive; it only refuses to run.
2. **Folder auto-detection.** The former personal folder (`UserFolder`, falling back to `%OneDriveConsumer%`, then `%USERPROFILE%\OneDrive` if it exists and is not a live sync root) is offered as the default `syncRoot` on first run, alongside `%USERPROFILE%\NoDrive`. The user chooses; the choice is written to `config.json`.
3. **Adoption of existing files (`adoptExistingFiles`, default true).** Because unlink leaves only locally available files, adoption is a reconciliation of ordinary files against the Graph index, not a migration of placeholders. After the first delta pass has filled the index, an adoption worker walks the folder with bounded concurrency and, per file:
   - path matches an index item and size + last-modified (second precision, UTC) match: `CfConvertToPlaceholder` + `CfSetInSyncState` in place, no download; quickXorHash verified lazily in the background and the item demoted to `LocallyModified`/conflict if it differs;
   - path matches but size/mtime differ: the local file is renamed `<name> (local copy YYYY-MM-DD)` (kept as a local-only file, uploaded under v1 upload-new rules) and a fresh placeholder is created for the cloud item;
   - path has no index item: treated as a new local file (v1 upload-new), then converted to a placeholder once the upload is acknowledged;
   - directories that exist locally become populated placeholder directories; directories only in the cloud are created lazily as usual.
   Adoption runs at low priority, is journaled and resumable, never blocks Explorer (it is just another worker behind the same bounded channels) and reports progress in the tray. Known-folder redirection (OneDrive "Back up folders" for Desktop/Documents/Pictures, which the user has enabled) is **not** adopted in v1. Detection: for FOLDERID_Desktop, Documents, Pictures, Screenshots and CameraRoll compare `SHGetKnownFolderPath(id, 0)` with the `KF_FLAG_DEFAULT_PATH` result; if any redirected path lies under the chosen root, adoption stops with a tray message pointing at the migration procedure below. Reason: no vendor other than Microsoft ships online-only known folders, and the shell interactions (Desktop view, wallpaper, Start menu, indexer, Storage Sense) are unverified (`research/known-folder-move.md`). Native support is a P2 feature built on `IKnownFolderManager::Redirect`.

   Whether folder backup is on at all is determined by `spikes/onedrive-state.ps1` (known-folder paths vs defaults); the user's PC is a personal notebook, so the most likely reasons the option is not visible are the relocated UI (Settings > Sync and backup > Manage backup) or backup simply being off (`research/known-folder-move.md` 1b).

   **Migration procedure for a user with folder backup on** (documented in README): (1) OneDrive Settings > Sync and backup > Advanced settings > Files On-Demand > Download all files, wait for solid check marks; (2) Settings > Sync and backup > Manage backup > turn Desktop, Documents, Pictures off one by one, choosing per folder between "Keep the files only in OneDrive" (cloud keeps them, local folder becomes empty, NoDrive later adopts them under `<root>\Desktop` etc.) and "Keep the files only on my PC" (moved back to `%USERPROFILE%\Desktop` etc. and deleted from the cloud, so they are no longer synced); (3) verify `User Shell Folders` / `SHGetKnownFolderPath` point to `%USERPROFILE%\...`; (4) only then Unlink this PC; (5) install NoDrive and adopt. Backup must be turned off before unlinking: community reports show unlinking first can leave the known folders pointing into the dead OneDrive folder.
4. **Hardening against re-provisioning.** `--status` reports whether OneDrive.exe is present and whether `DisableFileSyncNGSC` is set; the docs recommend setting it (and removing the `Run\OneDrive` entry) after unlinking. NoDrive does not write HKLM policy keys itself in v1 (needs elevation, and it is the user's machine policy).

## Consequences

Positive:
- A user with 200k items and hundreds of GB locally available does not re-download anything; adoption is metadata-only for matching files.
- Detection prevents the double-sync failure mode by construction and gives a clear, actionable message.
- All checks are read-only registry/API calls that work unelevated and cost nothing at idle.

Negative:
- Adoption adds a P1 epic (E1b) and a correctness surface: size + mtime equality is a heuristic; the lazy hash pass is what makes it safe, and until it has run a stale local copy could be served as "in sync". Mitigation: hash pass before enabling dehydration of adopted files; never dehydrate an adopted file whose hash has not been verified.
- Registry layouts are community-verified, not documented by Microsoft; a future OneDrive build can move them. Mitigation: the `SyncRootManager`/`CfGetSyncRootInfoByPath` check is the authoritative one and is documented; the `Accounts\Personal` read is a convenience that degrades to "not detected".
- Known-folder-redirected users must do a manual step before adoption.

Revisit when:
- Microsoft documents the OneDrive registry surface or changes the sync-root id format (test on each OneDrive major build).
- The user wants KFM folders inside the NoDrive root (would need research on `SHSetKnownFolderPath` interactions with third-party sync roots).
- The P0 spike shows `CfConvertToPlaceholder` on hundreds of thousands of files is too slow or hits the 24H2/25H2 heap-corruption class of bugs (then adoption falls back to "leave as normal files, upload-new only").
