# ADR-0001: Windows Cloud Files API (cfapi) over a custom Explorer-like client or a WinFsp/Dokany mount

## Status

Accepted 2026-11-13

## Context

NoDrive must give OneDrive-style "Files On-Demand" access to a personal OneDrive inside File Explorer, with minimal idle memory, and it must never hang Explorer. Three ways to expose remote files on Windows were researched.

### Option A: Cloud Files API (cfapi)

- cfapi is the platform OneDrive itself uses: `cldflt.sys` minifilter (built into Windows 10 1709+, NTFS only) + `CldApi.dll` Win32 functions + `Windows.Storage.Provider` WinRT registration. Registering a sync root yields, for free: placeholder files (~1 KB), the nav-pane node with icon, the Status column icons, the built-in "Always keep on this device" / "Free up space" verbs, inline/dialog/toast hydration progress. No kernel driver to install, no elevation. Source: https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine
- Mandatory provider surface is small: `FETCH_DATA` (unless hydration policy ALWAYS_FULL) and `FETCH_PLACEHOLDERS` (unless population ALWAYS_FULL); the rest of the 13 callback types are optional. Source: https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_callback_type
- The provider is an ordinary per-user, non-elevated, always-running desktop process; not a Windows service (session-0 hydration blocked; community-reported Q&A reproduction, GitHub issue #245 has no Microsoft reply). Source: https://learn.microsoft.com/en-us/answers/questions/892349/cfapi-allow-data-fetch-for-services , https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfconnectsyncroot
- Package identity is not required for registration, nav pane, Status column or built-in verbs (community-verified Nov 2026: https://github.com/B3nedikt/Tenshu/pull/6 ; Microsoft's `Unregister` docs explicitly address non-MSIX desktop apps: https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovidersyncrootmanager.unregister?view=winrt-26100 ). Identity is only needed for Windows 11 modern context-menu entries and manifest-declared extensions.
- All 36 `Cf*` functions are in Win32Metadata, so CsWin32 0.3.371 generates AOT-safe bindings. Source: https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Storage/CloudFilters/index.html
- Shipping third-party providers prove the route: Nextcloud and ownCloud (unpackaged, registry-based shell integration), Mountain Duck 5 "Integrated" mode (2025). Source: https://docs.mountainduck.io/mountainduck/connect/integrated/
- Risks: the fixed 60 s callback deadline (documented: https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_callback_type ); and, community-reported (Microsoft Q&A answered by external vendor moderators): `CfUpdatePlaceholder` heap corruption on 24H2/25H2 since Nov 2024; `NOTIFY_DEHYDRATE` not firing for "Free up space"; `CreateFileMapping` forcing full hydration. Explorer verbs moving into a per-provider flyout is from the Windows Insider blog. Sources: https://learn.microsoft.com/en-us/answers/questions/2120335/heap-corruption-after-using-cfupdateplaceholder , https://learn.microsoft.com/en-gb/answers/questions/1694157/when-will-cf-callback-type-notify-dehydrate-be-inv , https://blogs.windows.com/windows-insider/2025/11/21/announcing-windows-11-insider-preview-build-26100-7271-dev-beta-channels/

### Option B: Custom Explorer-like client (Avalonia 12 / WinUI 3 / WPF window)

- Must keep a UI framework resident to give access to files, which contradicts the idle-memory goal.
- Cannot deliver transparency: other apps' Open/Save dialogs, double-click, drag from Explorer and Office's save sequence only work on real files or placeholders. Drag-out of online-only files is the hard part. Source: https://docs.avaloniaui.net/docs/input-interaction/drag-and-drop
- odrive's `.cloud`/`.cloudf` stub-file approach is the historical example of this UX and is exactly what the user wants to avoid. Source: https://docs.odrive.com/docs/sync-your-odrive

### Option C: User-mode file system mount (WinFsp or Dokany, as rclone mount does)

- Both require installing a third-party kernel driver and a resident user-mode process with its own caching; neither yields placeholders, Status icons, hydration progress or the nav-pane node.
- WinFsp is GPLv3 with a FLOSS linking exception (only usable by a FLOSS NoDrive not bundled with proprietary software); commercial licence 2,400-6,000 USD per 3 years. Source: https://github.com/winfsp/winfsp/blob/master/License.txt , https://winfsp.dev/com/
- Dokany driver/library are LGPL-3.0 (dynamic linking from any licence is fine), dokan-dotnet MIT, v2.3.1.1000 (2025-09-28). Source: https://github.com/dokan-dev/dokany
- rclone mount's memory is dominated by in-RAM directory trees (0.5-1 KB per object) and per-open-file buffers; idle mounts of 100-500 MB are community-reported. Source: https://rclone.org/faq/ , https://forum.rclone.org/t/rclone-mount-using-lot-of-ram-memory/28760
- rclone never pursued cfapi (2020 forum thread, no maintainer decision). Source: https://forum.rclone.org/t/support-windows-cloud-files-api-and-placeholder-files/18591

## Decision

NoDrive is a cfapi sync-engine provider: an unpackaged, per-user, headless engine process that registers one sync root (`StorageProviderSyncRootManager.Register`, fallback `CfRegisterSyncRoot` + registry keys) under `%USERPROFILE%\NoDrive` and answers `FETCH_DATA`, `CANCEL_FETCH_DATA`, `FETCH_PLACEHOLDERS`, `NOTIFY_DELETE` and `NOTIFY_RENAME`. explorer.exe renders everything. No custom file browser, no WinFsp/Dokany driver.

Rules that follow:

- No I/O inside any cfapi callback: validate, enqueue to a bounded channel, return in microseconds; complete asynchronously via `CfExecute`.
- Every pending request has a watchdog well under the 60 s deadline, with `CfReportProviderProgress` at least every 15 s and an explicit failure completion when progress is impossible. A stuck request is never left pending.
- Delete/rename notifications are acknowledged immediately from local state; the remote operation is journaled and executed later.
- Connect with `CF_CONNECT_FLAG_REQUIRE_PROCESS_INFO | BLOCK_SELF_IMPLICIT_HYDRATION`; register with `AUTO_DEHYDRATION_ALLOWED`; never unregister on normal exit; never place the root at a drive root; NTFS only.
- Minimise `CfUpdatePlaceholder` (prefer `CfSetInSyncState` / `CfSetPinState`) until the heap-corruption repro passes on the target build.
- Keep a tray-menu fallback for "Free up space" / "Keep on this device" because the Explorer verbs are moving.

## Consequences

### Positive

- The lightest possible design: the engine is idle until a file is opened or a remote change arrives; no UI framework in the resident process.
- Transparent access from every application via placeholders; built-in progress, icons and verbs with no code.
- No driver installation, no elevation, no package identity in v1; single-developer scope is realistic (about 12 Win32 functions and 2-4 callbacks for an MVP).

### Negative

- Dependence on a platform with unresolved bugs and no real vendor support channel; a Windows update can change Explorer behaviour under us.
- The 60 s deadline and the "never block Explorer" requirement force an asynchronous, watchdog-driven design everywhere; a slow or blocking callback reproduces exactly the OneDrive.exe failure mode the user suffers.
- `CfUnregisterSyncRoot` is destructive (permanently deletes unhydrated placeholders): the uninstall flow must hydrate or warn.
- Windows only (and NTFS only); no macOS/Linux story from this layer.
- No end-to-end sample of a .NET/Native AOT cfapi provider exists; the P0 spike must prove callbacks and registration under AOT.

### Revisit when

- The P0 spike shows unpackaged `Register` does not produce the nav-pane node or Status icons on the target build, and `CfRegisterSyncRoot` + registry does not either.
- A Windows update breaks placeholders or hydration for third-party providers and is not fixed within a release cycle (keep the ability to fall back to a non-Explorer client).
- Microsoft documents cfapi as deprecated or restricts it to packaged apps.
