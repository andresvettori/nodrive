# ADR-0003: Hand-rolled authorization-code + PKCE with system browser, loopback listener and DPAPI; MSAL/WAM deferred

## Status

Accepted 2026-11-13

## Context

NoDrive needs delegated Microsoft Graph tokens for a personal Microsoft account from an unpackaged Native AOT desktop process, with the smallest possible dependency footprint.

### Evidence

- Microsoft fully documents the public-client flow: authorization-code + PKCE (`code_challenge_method=S256`) against `https://login.microsoftonline.com/consumers/oauth2/v2.0/authorize`, redirect `http://localhost[:port]` in the system browser, redeem at `/consumers/oauth2/v2.0/token` with `client_id`, `code`, `code_verifier`, `redirect_uri`, `grant_type=authorization_code` and no client secret; refresh with `grant_type=refresh_token`, a new refresh token is returned each time. Authorization codes expire in about 1 minute. Microsoft states it does "not recommend" manual protocol implementation over MSAL. Source: https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow , https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens
- Loopback redirect rules: `http://localhost` registered once, port ignored; IPv6 `[::1]` unsupported; no query strings or wildcards for MSA audiences. Source: https://learn.microsoft.com/en-us/entra/identity-platform/reply-url
- Scopes: `Files.ReadWrite` + `offline_access` suffice for delta, download, upload and `socketIo`. Source: https://learn.microsoft.com/en-us/onedrive/developer/rest-api/concepts/permissions_reference
- rclone (MIT) uses the same pattern with redirect `http://localhost:53682/` bound to `127.0.0.1:53682`, in production for years. Source: https://rclone.org/onedrive/
- MSAL.NET 4.92.0 (2026-10-29): core is `IsAotCompatible` since 4.77.1 (PR #5458), MIT, 3.28 MB. But the WAM broker path (`Microsoft.Identity.Client.Broker` -> `NativeInterop` 0.20.7) is netstandard2.0/net462 only, 21.65 MB nupkg, not covered by the AOT analyzer; `msalruntime.dll` cannot be bundled into a single-file Native AOT exe; open issue #6232 (Oct 2026) reports the system-browser loopback success response aborting under `PublishAot`. Sources: https://www.nuget.org/packages/Microsoft.Identity.Client , https://github.com/AzureAD/microsoft-authentication-library-for-dotnet/pull/5458 , https://github.com/AzureAD/microsoft-authentication-library-for-dotnet/issues/6232
- What WAM would add: Windows account picker, Windows Hello / FIDO, device-bound refresh tokens, SSO with the Windows-signed-in MSA. None is required for a single-account personal client.
- Token storage: `System.Security.Cryptography.ProtectedData` (DPAPI, CurrentUser scope) is in-box and AOT-safe; MSAL's own Windows cache extension also uses DPAPI.
- Day-one risk independent of the library: newly consented personal-account apps reported to receive `403 serviceReadOnly` / `503 itemDisabledDueToPendingProvisioning` (community-reported, no Microsoft reply): https://learn.microsoft.com/en-us/answers/questions/5983388/personal-onedrive-newly-consented-apps-get-403-acc

## Decision

Implement authentication by hand: authorization-code + PKCE (S256), system browser (`ShellExecute` on the authorize URL), an `HttpListener` on `http://127.0.0.1:{ephemeral port}` that receives the code exactly once, `state` and `nonce` verification, token redemption and refresh over the shared `HttpClient` with STJ source-generated DTOs, and the refresh token encrypted at rest with DPAPI (CurrentUser) under `%LOCALAPPDATA%\NoDrive`. The Graph layer sees only an `ITokenProvider` with `GetAccessTokenAsync(CancellationToken)`. MSAL and the WAM broker are deferred; if ever added they plug in behind the same interface, behind a feature flag, and only after a real `PublishAot` build is validated.

Rules that follow:

- Authority `.../consumers/...`; scopes `Files.ReadWrite offline_access` as in the plan (`openid`, and `User.Read`, only if an id_token or display name is ever needed).
- Never persist the access token; cache it in memory until 5 minutes before expiry. Persist only the refresh token, always replacing it with the newest one returned.
- On refresh failure with `invalid_grant`, mark the account signed-out, stop all Graph work, show a tray notification; never loop on sign-in.
- Loopback listener lifetime is bounded (a few minutes) and torn down on success, failure or cancel; the browser page it serves is a static "you can close this window".
- Sign-in runs in the engine but never on a cfapi callback thread, and never blocks hydration worker queues: while signed out, pending hydrations fail fast with a visible error.

## Consequences

Distribution model (added 2026-11-13): the app registration is created once by the publisher; the client ID is public and embedded in the binary as a default, and `config.json` may override it. End users never register anything; they consent at first sign-in. Shared client IDs share the per-app Graph throttling budget (rclone documents this for its shared OneDrive ID and recommends personal IDs), hence the override. Publishing beyond personal use needs branding (name, logo, publisher domain, privacy/terms URLs) and optionally Microsoft publisher verification to drop the "unverified" label on the consent screen. No client secret exists, so nothing secret ships; PKCE protects the code exchange.

### Positive

- Zero NuGet dependencies for auth; provably AOT-clean; nothing to bundle beside the exe.
- Full control of timeouts, retries and error surfacing, in line with the "never hang" requirement.
- The same flow works unchanged if MSA-only is later widened to `/common`.

### Negative

- We own the security details (PKCE, state, single-use code, listener hardening) and the test burden MSAL would carry.
- No Windows Hello, no SSO with the signed-in Windows account, no device-bound tokens; the user signs in through a browser once per device.
- Microsoft's guidance is to use MSAL; protocol changes (unlikely but possible) land on us.

### Revisit when

- MSAL + Broker publishes warning-free under `PublishAot` on net11 win-x64 as a single file and issue #6232 is fixed, and a user-visible benefit (Windows Hello, SSO) is wanted.
- Microsoft requires broker-based sign-in or restricts loopback redirects for MSA public clients.
- Multiple accounts or work accounts become a requirement.
