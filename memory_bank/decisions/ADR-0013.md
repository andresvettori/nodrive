# ADR-0013: Coexistence with the OneDrive app and adoption of identical files by name, size and modified time

## Status

Accepted 2026-11-16. Amends ADR-0008: the refuse-to-start rule is dropped.

## Context

The user keeps the OneDrive app installed (Folder Backup is on) and wants NoDrive to work next to it, and to leave OneDrive only when they choose. Two clients on one account behave like two computers. A reinstall of NoDrive (or taking over OneDrive's old folder) leaves ordinary files that are identical to their cloud copies; uploading them would create "conflict" duplicates. Downloaded files keep the cloud's modified time, so name + size + modified time identifies the same file cheaply; quickXorHash was not implemented.

## Decision

1. NoDrive never refuses to start because of OneDrive; it detects it read-only (process, `HKCU\Software\Microsoft\OneDrive\Accounts\Personal`, Known Folder redirection) and explains the situation on the settings page. It still refuses to register inside a folder another provider owns.
2. When a new local file or folder matches an index entry (same name in the same cloud folder; for files also the same size and modified time within 2 s), the upload service converts it to an in-sync placeholder and does not upload it; a cloud folder with the same name is linked and its files are matched one by one; different content gets the normal upload (conflict copy on a name clash).
3. The optional Switch from OneDrive assistant (settings page) offers a read-only scan, guidance for what only OneDrive can do (stop Folder Backup keeping files, unlink), and a take-over that sets the sync root to that folder, replaces the registration, sets `adopt.pending`, restarts, and links identical files while population is held back. It never unlinks, uninstalls or reconfigures OneDrive and never deletes or overwrites files.

## Consequences

### Positive
Reinstall and take-over do not duplicate files; no hashing cost; OneDrive stays untouched.

### Negative
A modified file with identical size and mtime would be linked instead of uploaded (very unlikely); during a large adoption folders answer "unavailable" until linking finishes; take-over needs OneDrive unlinked first.

### Revisit when
quickXorHash is implemented (verify on a sample), or Windows exposes a supported way to move a sync root.
